# Кодстайл (Assets/Code)

Этот документ фиксирует соглашения, которые уже используются в `Assets/Code`.

## Форматирование
- Использовать 4 пробела для отступов; табы не коммитить.
- Скобки для namespace, типов и многострочных членов ставить на отдельной строке (Allman).
- Для expression-bodied членов (свойства и методы) сигнатуру оставлять в первой строке, а реализацию всегда писать на следующей строке после `=>`. Это жёсткое правило даже для однострочной реализации; не писать выражение справа от `=>` в той же строке:
  ```csharp
  public bool HasCoins =>
      _coins > 0;

  public int GetCoinsCount() =>
      _wallet.Coins;
  ```
- Expression-bodied форму использовать только когда вся реализация — одно выражение в одну строку (после переноса).
- Если реализация не помещается в одну строку или содержит больше одного действия, использовать block body со скобками (`{ ... }`) для методов и `get { ... }` / `set { ... }` для свойств.
- Добавлять пустые строки между логическими секциями (`using`, поля, конструкторы, методы), но не накапливать несколько пустых строк подряд.
- Не выходить за правую направляющую IDE, принятую в проекте; если строка не помещается, переносить выражение (для expression-bodied членов применять правило выше и переходить на block body).
- Правая направляющая сама по себе не является поводом для переноса. Вызов метода, который читается как одно действие, оставлять в одну строку, даже если он вылезает за направляющую. Переносить только когда строка стала реально нечитаемой, а не когда линейка загорелась.
- Разрешены однострочные guard clauses без скобок, если тело состоит из одного выражения:
  ```csharp
  if (!_dialogueBackground)
      return;
  ```
- Не оставлять trailing whitespace ни в одной строке и не оставлять whitespace-only «пустые» строки: разделительная строка обязана быть по-настоящему пустой. Это относится и к строкам, которые правка только сдвигает.
- Правило про whitespace распространяется на файлы, которые пишем мы. Сериализованные Unity ассеты (`.unity`, `.prefab`, `.asset`, `.meta`, `.anim`, `.controller`, `.mat`) движок пишет сам и оставляет в них висящие пробелы; править их руками нельзя — при следующем сохранении Unity вернёт всё обратно.
- Сохранять формат окончания файла как в оригинале: если в файле не было завершающего перевода строки, не добавлять его; если был — не добавлять лишние пустые строки.

## Using-и и неймспейсы
- `using` директивы держать вне namespace.
- Порядок групп: `System` / `System.*`, project namespaces (`Code.*`), сторонние SDK, Unity namespaces, затем aliases (`using ILogger = ...;`).
- Не использовать `using static`; для конфликтующих типов использовать alias, например `using Object = UnityEngine.Object;`.
- Удалять неиспользуемые `using` при любой правке файла.

## Типы
- Один top-level тип на файл; имя файла совпадает с публичным типом.
- Не объявлять вложенные типы внутри классов/структур (`class`, `struct`, `record`, `enum`, `interface`, `delegate`). Все типы размещать только на top-level (один уровень файла/namespace). Исключение одно — данные extension-класса, оно описано ниже.
- Исключение для state-моделей: в файле state допускается второй top-level тип payload (`<StateNameWithoutState>Payload`), при этом payload размещается выше state-класса, а базовая часть имени должна совпадать.
- Исключение для extension-классов: данные, которые существуют только как вход или результат их методов, объявляются вложенными типами в самом конце extension-класса, после всех методов. Снаружи к ним обращаются через имя класса: `BroomLayoutExtensions.CoinMoveData`. Так видно, что тип принадлежит расчёту и сам по себе никому не нужен. В отдельный файл тип уходит, только когда им начинают пользоваться в обход extension.
- Файлы, которые содержат только наборы констант, именовать с суффиксом `Constants`.
- `class`, `struct`, `enum`, `delegate` использовать в `PascalCase`. MonoBehaviour/сервисы помечать `sealed` только когда наследование действительно нужно запретить.
- Акронимы и общепринятые аббревиатуры в именах типов и методов писать в верхнем регистре (`IAP`, `SDK`, `UI`, `API`), не смешивать с вариантами вроде `Iap`/`Sdk`. Идентификаторы и GUID называть в принятой проектом C#-форме `Id`/`Guid`: `ParentSlotId`, `TargetSlotId`, `UniqueId`, `Guid`.
- Интерфейсы начинаются с `I` (например, `IBackgroundIndexService`), элементы enum в `PascalCase`.
- `ScriptableObject` конфиги публиковать через Unity-атрибуты (`[CreateAssetMenu]`); сериализуемые поля оставлять `public` только когда это действительно authoring data.
- UI MonoBehaviour называть по домену без искусственных суффиксов (`Island`, `IslandAnimator`, `IslandConfig`); `Item` использовать только для повторяемых UI-элементов (карточки, кнопки, элементы списков).
- Повторяемый UI-элемент называется `<Домен>Item`, даже если весь он кликается как кнопка: `BoosterItem`, а не `BoosterButton`. Суффикс `Button` остаётся только у самого компонента-кнопки (`BoardButton`, `DealButton`), а не у элемента, внутри которого кнопка лежит. Событие нажатия у такого элемента называется `ButtonClicked`, поле с ним в родителе — `<Домен>Item` (`BroomItem`, `HammerItem`). Родительский компонент, который держит такие айтемы, называется по своей роли (`BoardHUD`), а не `<Домен>Buttons`: он не кнопка и не набор кнопок.
- Компонент, который наполняет канвасы `<Что>HUD`, называется `<Домен>HUD` и размещается по правилу структуры модулей в `<Фича>/Behaviours/` (`Level/Behaviours/LevelHUD`, `Board/Behaviours/BoardHUD`). Метод, наполняющий конкретный канвас, называется по нему: `UpdateLockedHUD`, `UpdateExtraTrayHUD`, `UpdateCountdownHUD`. Безликие `*Labels`, `*Texts` не использовать: по ним не видно, какой именно канвас меняется.
- Entitas-компоненты обязаны использовать суффикс `Component`, если их имя совпадает с runtime-типом проекта (`MonoBehaviour`, service, config, animator и т.д.); Jenny убирает этот суффикс в сгенерированных matchers/API.
- В gameplay/meta/domain naming не использовать суффиксы `View` и `Controller`. Исключение - инфраструктурный view-layer (`IEntityView`, `EntityBehaviour`, `ViewPrefab`, registrars/bindings вокруг entity views), где термин отражает техническую границу.

## Поля и свойства
- Приватные поля: `_camelCase`; для зависимостей из конструктора/инжекта предпочитать `readonly`.
- Константы: `const` с именами в `UPPER_SNAKE_CASE` (`PROGRESS_KEY`).
- `const` всегда писать только в `UPPER_SNAKE_CASE`. Для `public`/`internal`/`private` `const` исключений нет.
- `static readonly`, используемые как именованные константные значения, всегда писать в `PascalCase` (`ProgressKey`).
- Технические литералы, у которых есть смысл (индекс материала в renderer, индекс слота, размер буфера, шаг цикла), выносить в `const` с говорящим именем и не писать голым числом в вызове. Балансные и дизайнерские числа при этом остаются в конфиге, а не в `const`.
- Не смешивать стили между `const` и `static readonly`. `const` не должен называться в `PascalCase`, а `static readonly` не должен называться в `UPPER_SNAKE_CASE`.
- Доменные типы и свойства называть нейтрально по предметной области; не использовать в доменных моделях (`GameItem`, конфиги, gameplay сущности) аналитические/трекинговые названия.
- Суффикс `Config` носит корневая модель статик-данных независимо от носителя: и `ScriptableObject`, и класс, который читается из JSON (`BoostersConfig`, `DealConfig`). Обычный `[Serializable]`-класс, который лежит внутри конфига полем или элементом списка, конфигом не является и называется с суффиксом `Data`: `DealFillRuleData`, `RewardData`, `PriceData`. Это же правило действует для любых plain-контейнеров данных вне static data.
- Поле, локальная переменная и параметр, хранящие конфиг, называются полным именем своего типа в `camelCase`: `ChipNumbersConfig chipNumbersConfig`, `HeartsConfig heartsConfig`, `ChipPaletteConfig chipPaletteConfig`. Имя обязано заканчиваться на `Config`, а перед суффиксом обязана стоять доменная часть.
- Отбрасывать `Config` из имени запрещено: `_numbers`, `palette`, `number`, `color` не читаются как конфиг, и в месте использования нельзя понять, что это static data, а не доменная сущность.
- Голое `config`/`_config` тоже запрещено: когда в методе появится второй конфиг, различить их будет нечем, а по сигнатуре helper-метода не видно, какой именно конфиг он берёт.
- Исключение: параметр лямбды внутри одного выражения (`Numbers.Find(config => config.Id == id)`) — он живёт одну строку, и тип читается по самой коллекции.
- Имя коллекции обязано называть то, что в ней лежит, а не соседнее понятие. `List<BoardSlotSnapshot>` — это `slotSnapshots`, а не `slots`: сокращение до «слотов» переносит имя на другую сущность и читается как список самих слотов. Это же относится и к методу, который такую коллекцию возвращает.
- Для остальных полей, локальных переменных и параметров выбирать самое короткое имя, которое остаётся однозначным в своём scope. `_requests`, `_actions`, `_entities`, `_buffer`, `_factory`, `service`, `animator` допустимы, если тип, класс и единственный объект этой роли полностью объясняют смысл; механически повторять полное имя типа не нужно. Доменное уточнение добавлять, когда объектов одной роли несколько или без него назначение действительно теряется: `_slotBuffer` и `_chipBuffer`, `_dialogueFactory` и `_entityViewFactory`.
- Один сериализуемый параметр — ровно одна строка с объявлением. Атрибуты `SerializeField` и `Range` писать в той же строке перед объявлением. `Header` — исключение: писать его на отдельной строке непосредственно над первым параметром секции; перед каждым не первым `Header` оставлять одну пустую строку. Внутри секции пустые строки между параметрами не ставить.
- `[FormerlySerializedAs]` запрещён полностью — и как атрибут поля, и в форме `[field: FormerlySerializedAs]`. Переименование сериализуемого члена доводить до конца руками: переименовать `<Old>k__BackingField` на `<New>k__BackingField` во всех `.prefab`, `.unity` и `.asset`, где он встречается, и проверить, что значения на месте. Атрибут-миграция оставляет мусор в коде навсегда ради разовой правки данных.
- Inspector-состояние сериализовать через auto-properties с `[field: SerializeField]`, чтобы сохранять инкапсуляцию:
  ```csharp
  [field: SerializeField] private Button CloseButton { get; set; }
  ```
- Для `DialogueBase`-наследников с собственными serialized fields обязательно добавлять над их блоком `[field: Header("...")]`.
- Текст `Header` для диалога писать по производному имени класса без суффикса `Dialogue` (`ReviewEntryDialogue` -> `Review Entry`, `WinStreakDescriptionDialogue` -> `Win Streak Description`).
- Если у `DialogueBase`-наследника нет собственных serialized fields, отдельный `Header` не нужен.
- Внутри класса сериализуемые/публичные/защищённые свойства размещать выше приватных полей, чтобы сначала шла наблюдаемая поверхность.
- Публичные изменяемые поля использовать редко; в основном в data-контейнерах (ScriptableObject, простые MonoBehaviour).
- Для простых однострочных getter-ов предпочитать expression-bodied свойства:
  ```csharp
  public DialogueBase OpenDialogue =>
      _dialoguesQueue[0];
  ```
- Метод и свойство, которые возвращают `bool`, называются вопросом: `Is...`, `Has...`, `Can...` (`IsSlotBusy`, `IsCoinSelectable`, `HasBroomMoves`, `CanTickTimer`). Утвердительная форма (`SlotIsBusy`, `MoveIsValid`, `BoardHoldsGoalCoins`) не используется. `Try...` с `out`-параметром остаётся как есть.
- Составное условие готовности или доступности, которое отвечает на один смысловой вопрос,
  выносить в приватное вычисляемое свойство (`CanTickTimer`, `CanInteract`). Тогда основной метод
  читается как сценарий, а детали правила раскрываются только при необходимости. Решение принимать
  по смыслу, а не по числу операторов: не выносить одноразовую простую проверку и не прятать условие,
  детали которого являются частью читаемого flow самого метода.
- Если getter/setter не однострочный, раскрывать accessor в block body (`get { ... }`, `set { ... }`).

## Комментарии
Перед коммитом любой правки проверять diff на добавленные комментарии.

- Комментариев в коде нет: ни `//`, ни `/* */`, ни `/// <summary>`. Мы не пишем документацию. Код объясняет себя понятными именами, короткими методами и местом в архитектуре.
- Пересказ логики, причина правки, история бага и ссылка на источник — не комментарий в коде. Если это важно, место ему в описании PR.
- Если строку хочется пояснить, сначала переименовать сущность, вынести условие или выделить метод. Комментарий не заменяет рефакторинг.
- Исключения — редкие звери, единицы на весь проект: подсказка хоткея рядом с `MenuItem` (`// Command + G`); неочевидное требование движка, платформы или SDK, которое не выразить кодом (порядок исполнения скрипта, как в `SwitchToEntrySceneInEditor`); секции `// Arrange`, `// Act`, `// Assert` в тестах.
- Сомнение, подходит ли случай под исключение, означает, что не подходит.
- Существующие комментарии в легаси попутно не удалять: чистку решает владелец. Новых не дописывать.

## Порядок членов класса
- Использовать единый порядок членов внутри класса/структуры:
  1. `const` и `static readonly` поля.
  2. События (`event`) (public -> protected -> private).
  3. Свойства.
     Это относится и к `private` member'ам: даже private/computed properties размещать выше private fields.
  4. Поля (`[SerializeField]`/public/protected/private).
  5. Конструкторы.
  6. `[Inject] private void Construct(...)` (если есть).
  7. Public методы инициализации (`Initialize`, `SubscribeUpdates`, и аналогичные init-методы).
  8. Unity lifecycle methods (`Awake`, `OnEnable`, `Start`, `Update`, и т.д.) в порядке выполнения.
  9. Public cleanup методы (`CleanUp`, `Dispose`, `Unsubscribe`, и т.п.).
  10. Остальные public методы.
  11. Protected/internal/private методы.
  12. Callback/handler методы (`On...`) размещать в самом низу файла.
- Между секциями оставлять пустые строки, чтобы структура читалась сразу.
- Внутри блока `const` / `static readonly` сначала всегда размещать все `const`, ниже — все `static readonly`.
- Между последней `const` и первой `static readonly` всегда стоит ровно одна пустая строка-разделитель. Это два разных блока, слипаться они не должны никогда.
- Для интерфейсов обязательно разделять пустой строкой блоки `event`, свойств и методов.
- В интерфейсе свойства внутри своего блока идут подряд, без пустых строк между ними. В классе наоборот: между свойствами всегда стоит пустая строка, каждое свойство — отдельный блок. Блок `event` в классе, как и в интерфейсе, остаётся слитным.
- Свойства класса внутри своей секции располагать по видимости: `public`, затем `protected`/`internal`, затем `private`. Публичное свойство не оставлять посреди блока приватных computed properties.
- Для `private`/`protected` helper-методов внутри одной секции соблюдать порядок по call-flow:
  - сначала держать единый блок `public` методов, а весь `private`/`protected` call-flow располагать уже после него;
  - внутри `private`/`protected` секции группировать методы по веткам: метод-вызыватель, сразу под ним его helper-методы, затем helper-методы этих helper-методов и так далее вниз по цепочке;
  - к следующей независимой private-ветке переходить только после того, как текущая ветка полностью размещена целиком;
  - порядок самих верхнеуровневых private-веток выбирать по читаемости и связанности private-секции, а не пытаться механически повторять порядок `public` методов;
  - utility-методы без собственной ветки (`LeftToRightSide`, small converters/checkers) размещать в самом низу этой секции.

## Методы
- Всегда явно указывать возвращаемый тип (`void`, `int`, и т.д.); `var` для сигнатур не использовать.
- Для dependency injection использовать конструкторы или `[Inject] private void Construct(...)`.
- `LazyInject<T>` не использовать.
- Полевая инъекция (`[Inject]` на поля/свойства) запрещена.
- Если используется method injection, применять только `[Inject] private void Construct(...)` (без альтернативных имен и без дополнительных DI-методов).
- Методы вида `Set...(...)`, которые агрегируют внешнюю зависимость/объект (composition/aggregation), считаются частью инициализационного блока и размещаются рядом с `Construct`/`Initialize`.
- Expression-bodied методы допустимы только для одного однострочного выражения (по общему правилу переноса после `=>`); при нескольких выражениях, ветвлениях или многострочной реализации переходить на block body.
- Не выносить в отдельный метод короткую цепочку из двух-трёх вызовов только потому, что она повторяется в нескольких обработчиках. Звук и вибрация по нажатию кнопки пишутся прямо в каждом `On...Click`, а не в `PlayButtonFeedback()`. Метод-обёртка над парой вызовов не убирает логику, а только прячет, что именно происходит по клику. Выносить стоит расчёт, ветвление или повторяемую последовательность с собственным смыслом.
- Если callback не принимает аргументы и только вызывает один метод, использовать `method group` (конверсия группы методов) вместо пустой лямбды: `onDone: SomeMethod` вместо `onDone: () => SomeMethod()`.
- Для declaration методов/конструкторов/делегатов параметры можно переносить вертикально, по одному на строку. Это относится только к месту объявления сигнатуры в классе/интерфейсе.
- В call-site вертикальный формат "каждый аргумент на своей строке" запрещён. При вызове метода аргументы держать в строке до правой направляющей IDE и переносить только компактный хвост, который уже не помещается.
- Исключение для Entitas matcher composition: если `AllOf(...)` или `NoneOf(...)` содержит больше одного matcher-компонента, раскрывать вызов вертикально, по одному matcher-у на строку. Это описание состава выборки, а не обычный call-site.
- В местах вызова методов держать аргументы в одну строку, если выражение помещается.
- Если вызов не помещается:
  - оставлять имя метода и первый помещающийся аргумент в первой строке;
  - заполнять не только первую, а каждую строку вызова аргументами максимально до правой направляющей IDE (не переносить раньше времени);
  - переносить только тот хвост аргументов, который уже не помещается;
  - переносить аргументы компактным хвостом (по несколько аргументов в строке, пока помещается);
  - не переносить каждый аргумент на отдельную строку без необходимости;
  - не оставлять пустую первую строку сразу после `(`, если первый аргумент помещается.
- Запрещённый anti-pattern для call-site: перенос сразу после `(` и каждый аргумент на отдельной строке. Правильная форма — оставить максимум аргументов на первой строке и перенести только оставшийся хвост:
  ```csharp
  // Bad
  service.Do(
      first,
      second,
      third,
      fourth);

  // Good
  service.Do(first, second, third,
      fourth);
  ```
- Именованные аргументы в местах вызова по умолчанию не использовать. Считать их запрещёнными, кроме действительно редких исключений, когда без них вызов становится неоднозначным или теряет смысл из-за неочевидного литерала (`true`, `false`, `null`, числа без контекста).
- Не разбрасывать повторяющиеся null-check для serialized fields и injected dependencies в каждом методе; автор отвечает за корректную конфигурацию ссылок, guard clauses добавлять только при реальной runtime-неопределённости.
- Не добавлять null-check и null-propagation (`?.`, `??`) для serialized fields, injected dependencies и config data. Отсутствующие ссылки — это setup error, он должен падать сразу.
- После присваивания параметра в поле или свойство по умолчанию продолжать работать с исходным параметром, а не с только что присвоенным членом класса.
- Исключение: если дальнейший порядок действий явно зависит от уже обновлённого состояния объекта/сервиса, после присваивания работать именно через поле/свойство. Такой код должен визуально подчёркивать причинно-следственную связь: сначала обновляем состояние (`CurrentScreen = screen`), потом выполняем действия, завязанные на это состояние (`CurrentScreen.Initialize()`).
- Не оставлять неиспользуемый код: публичный метод конфига или сервиса без единого вызывающего, приватный helper без вызова, локальную переменную без чтения, параметр конструктора без присваивания. Такой код удалять в том же изменении, где он стал лишним.
- Это правило про код, ставший лишним навсегда. На код и ассеты временно выключенной механики оно не распространяется: см. `AI_COLLABORATION_GUIDELINES.md`, раздел Temporarily Disabled Mechanics.
- Не добавлять API «про запас»: метод заводить в момент появления первого вызывающего, а не заранее рядом с похожим.
- Держать lifecycle-пары (`Initialize`/`CleanUp`, `SubscribeUpdates`/`CleanUp`) рядом, подписки и listeners снимать симметрично.
- Предпочитать guard clauses, чтобы уменьшать вложенность.
- Если несколько подряд guard clauses выполняют одно и то же действие (`return`, `return false`, `continue`, `break`, `throw`), объединять их в один `if` через логические операторы.
- Не разбивать один и тот же early-exit на цепочку из нескольких `if`, если все они ведут к одному и тому же действию выхода. В таких случаях по умолчанию писать один объединённый guard.
- Для объединённого `if`: если условий больше двух или выражение длинное, переносить каждое условие на новую строку.
- Ширина: ориентир 120 символов, приоритет у читаемости. Строку, вылезающую на пару символов, ломать не нужно, если перенос прячет смысл; переносить обязательно, когда строка перестаёт читаться целиком.
- «Длинное» означает, что строка не помещается в 120 символов. Два условия, влезающие в строку, переносить нельзя: перенос ради красоты добавляет строку и прячет, что проверка одна. Сначала пробуем уместить целиком, и только если не влезает — переносим каждое условие на свою строку.
- Если строка не влезает из-за длинного обращения, а не из-за числа условий, сначала вынести это обращение в локальную переменную с говорящим именем, и только потом переносить условие.
- При переносе логический оператор остаётся справа, в конце строки: `a > 0 ||` и следующее условие с новой строки. Оператор в начале строки запрещён. Читаем сверху вниз, и связка обязана быть видна в той строке, которую она продолжает, а не в следующей.
- Если условие перенесено на несколько строк, тело обязано быть в скобках, даже когда в нём один `continue`, `return` или `break`. Без скобок закрывающая строка условия и тело выглядят одинаково, и глазом их не развести: перенос уже съел единственный признак, по которому тело отличалось от условия. Однострочное условие с однострочным телом скобок по-прежнему не требует.
- Создание сущности builder-chain-ом — отдельная мысль: после закрывающей строки chain-а идёт пустая строка. Изменения состояния, которые следуют за созданием, между собой не разделяются и пишутся одним блоком.
- В теле метода блоков обычно два-три, а не по одному на строку. Прежде чем ставить пустую строку, ответить, какая законченная мысль на ней кончилась; нет ответа — строка лишняя.
- Критическая последовательность, которая обязана отработать в одном кадре подряд, пустыми строками не разрывается: создание сущности цикла и изменения состояния, ради которых цикл заведён, пишутся вплотную. Разрыв читается как «между этими шагами можно вклиниться», а вклиниваться там нельзя.
- Вызов собственного метода не ставить между однородными построчными операциями над сущностями: он идёт до или после такой группы. Смешанный список читается как одна последовательность, хотя один его элемент разворачивается в отдельный сценарий. Образец — `RestartLevelState.Enter`: сперва свои методы, потом вызовы сервисов. Пустой строкой от группы он при этом не отделяется — блоки внутри одного сценария разделяются по общему правилу ниже, а не по факту вызова.
- Блок из двух строк и меньше пустых строк внутри не содержит: тело метода, `for`, `foreach`, `while`, `if`, `else`, `using`, `lock`. Две строки читаются одним взглядом, и разрыв внутри них делит то, что делить не на что. Пустая строка появляется с третьей строки тела и только там, где на ней действительно кончилась законченная мысль. Тела типов сюда не относятся: там разделение членов пустой строкой задано отдельными правилами выше.
- Локальную переменную заводить только когда она сокращает выражение или даёт имя тому, у чего его нет. Переменная, которая просто повторяет свойство под другим именем (`bool showsOwnStatus = slot.isExtraTraySlot;`), запрещена: читателю приходится держать в голове два имени одного факта. Именовать имеет смысл составное условие целиком, а не его слагаемое.
- Значение, которое система берёт из конфига и использует в нескольких местах, выносить в приватное свойство класса, а не в локальную переменную в начале `Execute`. Переменная в `Execute` живёт весь метод, даже когда нужна в одной ветке, и раздувает шапку сценария.
- Возврат фабрики или сервиса не продолжать вызовом в той же строке: `Open<T>()`, `Create<T>()` и подобное сначала кладут в локальную переменную, а работа с результатом идёт следующей строкой. Цепочка прячет, что объект вообще создан, и ломает точку останова.
- Пустая строка внутри метода отделяет одну законченную мысль от другой, а не строки друг от друга. Две подряд идущие строки, где вторая работает с результатом первой, — это одна мысль, и разрывать её нельзя: `GameEntity slot = CreateSlot(board, slotIndex);` и `CreateCoins(slot, ...)` пишутся вплотную. Правило не про `return`, оно про любое место в теле метода, включая тело цикла и ветку `if`.
- Проверка простая: если убрать первую строку, вторая перестанет компилироваться или потеряет смысл — значит это одна мысль и пустой строки между ними нет.
- Перед `return` и `yield break` оставлять одну пустую строку, если в текущем методе/ветке больше двух исполняемых строк.
- Исключение: если метод/ветка по сути состоит только из двух строк, где первая что-то делает, а вторая сразу `return` или `yield break`, дополнительную пустую строку перед ними не ставить.
- Новые объявления дописывать в конец списка: компонент в файле компонентов, поле в классе, константу в generated-lookup, где индекс позиционный.
- К системам внутри feature это не относится: там место определяет порядок исполнения, а не история добавления. Система встаёт в ту фазу, где обязана отработать, даже если это середина файла.
- Про порядок объявления в остальном: Порядок объявления — это история появления, по нему читается, что было раньше; вставка сверху её переписывает. Сортировки по алфавиту у нас нет.
- Для сериализуемого поля-коллекции в `ScriptableObject` инициализатор `= new()` не писать: Unity сама создаёт пустую коллекцию при загрузке ассета. Инициализатор оставлять только там, где объект собирает не Unity: JSON-конфиги, обычные классы, `ProgressData`.
- Порядок гарантируется архитектурой, а не проверками. Не писать защитные `if` вида «а вдруг уже создано», «а вдруг ещё не готово», «а вдруг вызовут второй раз». Если такая проверка понадобилась, это сигнал, что неверен порядок инициализации или время жизни владельца; чинить нужно порядок, а не добавлять guard.
- Не закладывать заготовки под будущие миграции формата данных. Формат меняем — чиним по факту изменения, а не заранее.
- Не добавлять fallback-логику между конфигом и runtime-сервисом “на всякий случай”. Если значение обязано приходить из конфига, сервис должен возвращать его напрямую; проблемы править в конфиге, а не маскировать дополнительными проверками.
- Для конечного набора режимов использовать `switch` expressions/statements, с явными `break`.
- Исключения бросать через `IExceptionProvider`, если он доступен; иначе использовать стандартные framework exceptions (`ArgumentException` и т.д.).
- Пустой `catch` пишется только с конкретным типом ожидаемого исключения и без комментария: `catch (OperationCanceledException) { }`. Тип сам говорит, что гасим осознанно, и IDE перестаёт просить комментарий.
- Общий `catch { }` или `catch (Exception) { }` с пустым телом и пометкой «ignore» не писать. Если внутри `try` нечему бросать, убрать `try` целиком; если ошибка ожидаема, назвать её тип.

## Коллекции и аллокации
- Коллекции создавать с явным типом (`new List<DialogueBase>()`) или target-typed `new()`, если тип переменной очевиден:
  ```csharp
  private readonly List<EventTrigger.Entry> _entries = new();
  ```
- Локальные переменные объявлять с явным типом; `var` не использовать.
- При создании объекта через присваивание не переносить `new` на отдельную строку само по себе.
  Предпочтительный формат:
  ```csharp
  SomeService service = new SomeService(dependencyA, dependencyB);
  ```
- При присваивании результата вызова метода не переносить сам вызов на следующую строку сразу после `=`, если правая часть помещается целиком.
  Предпочтительный формат:
  ```csharp
  ReviewFeedbackDialogue dialogue = DialogueService.Open<ReviewFeedbackDialogue>(DialogueOpenMode.PushClosePrevious);
  ```
- Если присваивание с вызовом не помещается в одну строку, в первой строке всё равно оставлять `= MethodName(` и переносить только тот хвост вызова, который уже не помещается.
- Если вызов с аргументами не помещается в одну строку, применять общее правило для call-site: оставлять аргументы максимально плотно и переносить только тот хвост, который уже не помещается.
- В обычных местах вызова заполнять строку аргументами до предела читаемой ширины; не раскладывать каждый аргумент на отдельную строку по шаблону.
- Не использовать формат, где каждый аргумент вызова по умолчанию уходит на отдельную строку.
- Переносить параметры по одному на строку допустимо только в сигнатурах методов/конструкторов/делегатов по общему правилу проекта, а не в обычных местах вызова.
- Разрывать присваивание перед `new` допустимо только если без этого сигнатура/тип не помещается по ширине и другой читаемый перенос невозможен.
- Использовать существующие helper extensions (`ForIntCountedItem`, `SetState` и т.д.) вместо копирования логики.

## Паттерны Unity
- MonoBehaviour обычно должны иметь `Initialize`, где регистрируются подписки, и парный `CleanUp`, где они снимаются.
- Подписки на кнопки/события выполнять в `Initialize`, а в `CleanUp` снимать через `RemoveListener`.
- Когда нужны расчёты размера/пропорций, сначала вычислять локальные константы и выходить рано, если менять ничего не нужно.
- `Update` держать максимально лёгким.
- Coroutine (`IEnumerator`) объявлять только внутри `MonoBehaviour` и запускать только его собственным `StartCoroutine`. В state, service, provider, factory и adapter корутин быть не должно — там используется `async`/`await`; обязательные правила границы см. в `STATE_FLOW_AND_ASYNC.md`.
- Методы-корутины, возвращающие `IEnumerator`, именовать с суффиксом `Coroutine` (например, `PlayAppearCoroutine`).
- Ожидания в async-коде писать через `Awaitable` (`NextFrameAsync`, `EndOfFrameAsync`, `WaitForSecondsAsync`) и `await` над `AsyncOperation`, а не через corutine-обёртки и `TaskCompletionSource`.
- Platform-dependent код оборачивать в preprocessor directives с корректными отступами:
```csharp
#if !UNITY_EDITOR && (UNITY_ANDROID || UNITY_IOS)
    _notificationPermissionService.OpenAppSettings();
#endif
```
- Проверка, которая нужна только из-за ограничения одной платформы или одного редактора, живёт под директивой этой платформы (`#if UNITY_EDITOR_LINUX`), а причина пишется в тексте лога, а не комментарием. На остальных платформах такая ситуация остаётся ошибкой настройки и падает громко.

## Логирование и диагностика
- Для логирования инжектировать `ILogger`; предпочитать `_logger.Log(this, "...")` вместо прямого `Debug.Log`.
- Не дублировать источник лога в тексте сообщения (`[Notifications]`, `[Shop]`), если источник уже передаётся через `this`.
- Предположения валидировать явно и выходить рано, если состояние не позволяет продолжать (`if (IsQueueEmpty) return;`).
- Для null-check, которые не должны срабатывать, бросать исключения через `IExceptionProvider` для единообразных сообщений.

## Редакторные скрипты
- Editor-классы делать `static`, если это только меню-команды или helper-функции.
- Menu-команды регистрировать через `[MenuItem("Rokot Games/...")]`.
- Editor-скрипты обычно работают с `PlayerPrefs`, файловой системой проекта или selection state; перед потенциально разрушительными действиями ставить проверки и логировать результат через общий logger.
- Внутренние scroll-области внутри editor tools (`EditorWindow`, custom tools) прятать под foldout/collapse, чтобы они не перехватывали основной scroll окна в обычном состоянии.
