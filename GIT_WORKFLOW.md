# Git Workflow

Этот документ фиксирует единственный рабочий flow веток, коммитов, pull request, review и merge.

## Основной процесс

- В `main` напрямую не коммитить и не пушить. Любая работа попадает в `main` только через pull request.
- Каждую новую самостоятельную задачу начинать в отдельной task-ветке от актуального `origin/main`. Постоянную общую рабочую ветку не использовать.
- Перед первым изменением ассистент сам проверяет открытые PR и ветки, обновляет локальный `main`, удаляет уже смерженные task-ветки и создаёт подходящую ветку. Пользователю не нужно заранее придумывать имя или отдельно напоминать об этом.
- Граница ветки определяется одной цельной задачей и будущим PR, а не днём, неделей, спринтом или числом коммитов. В одной ветке допустимо сколько угодно фокусных коммитов, пока они обслуживают одну цель.
- Новую несвязанную задачу вести в новой ветке. Если scope текущей работы заметно изменился, не расширять старую ветку молча: отделить новую цель в свою ветку от актуального `main`.
- Несколько независимых task-веток и PR могут существовать одновременно. Это нормальный способ вести параллельные или отложенные задачи.
- Продолжение и исправления уже открытого PR делать в его исходной ветке. Новый push автоматически обновляет тот же PR; закрывать и создавать его заново не нужно.
- Явная просьба владельца «принести MR», «обновить MR» или продолжить правки в текущем MR считается согласованием push: после проверки коммита ассистент сразу отправляет изменения в удалённую ветку этого PR, если владелец отдельно не попросил оставить их локально.
- Push по умолчанию делается сразу: коммит в ветку существующего PR уходит на origin следом за проверкой сборки, без отдельного разрешения. Ветка, отставшая от локальной, — это не нейтральное ожидание, а поломка: владелец в панели и на GitHub читает устаревший код, а IDE при переключении предлагает `Drop Local Commits` и сносит работу одним кликом.
- Оставлять коммиты локально можно ровно в двух случаях: владелец прямо сейчас идёт по этому PR, либо он явно попросил не пушить. Это исключения с названной причиной, а не режим по умолчанию, и оба заканчиваются push сразу после того, как причина отпала.
- Если коммит всё же остался локальным, сказать об этом в ответе одной строкой и назвать причину. Молча оставлять расхождение между локальной веткой и origin нельзя.
- Запреты на push формулируются через условие («пока владелец ревьюит»). Прежде чем применить такой запрет, проверить, что условие выполняется сейчас. Запрет с невыполненным условием не действует и не превращается в осторожность по умолчанию.
- Заметка в хендоффе, договорённость прошлой сессии и вывод хука правилами не являются. Правила живут только в `_guidelines/` и в `CLAUDE.md` проекта; остальное — контекст, который не отменяет записанное и не ужесточает его.
- Куда класть правку — существующий PR или новый — решает ассистент сам, не спрашивая. Это относится и к работе по своей инициативе, и к просьбе владельца «сделай MR»: маршрут выбирается по содержанию, а не уточняется вопросом.
- Критерий один: правка идёт в открытый PR, если она по теме этого PR или лежит в файле, который он уже правит. Иначе — новый PR от актуального `main`. Правка не по теме, воткнутая в чужой PR, раздувает ревью; правка в файле стека, вынесенная в `main`, гарантирует конфликт при пропагации.
- Найденные попутно мелкие дефекты ассистент чинит сам, по тому же критерию, и не выносит их отдельным вопросом. Вопрос владельцу остаётся только там, где решение не техническое: продуктовое поведение, приоритет, порядок merge.
- О каждом таком решении ассистент пишет в ответе: что поправил, в какой PR положил и почему именно туда. Если правка ушла в PR, который владелец уже смотрит, сказать об этом прямо, чтобы он перечитал изменившийся кусок.

## Ревью pull request

- По умолчанию PR после реализации открывает ассистент; владелец также может открыть его самостоятельно.
- Ревью проводить в панели Pull Requests в Rider или в браузере GitHub — результат одинаковый.
- Замечания не требуют закрывать или отклонять PR: ассистент исправляет их в той же ветке и пушит туда же, после чего существующий PR обновляется автоматически.
- Не пушить в ветку открытого PR, пока владелец его ревьюит или мержит. Смена head перезапускает проверку мержабельности на сервере и гасит пункты merge в панели. Дополнения к открытому PR ассистент согласовывает до push.
- Доработку открытого, ещё не влитого PR не выносить отдельным PR поверх него. Иначе reviewer читает родителя, а потом узнаёт, что половина уже работает иначе. Если владелец сейчас смотрит PR, согласовать push и положить правку в тот же PR.
- Если после смены head панель Pull Requests залипла на `Checking branch for conflicts` и пункты merge остались серыми, Refresh и переоткрытие вкладки не помогают: лечится рестартом IDE. Фактическое состояние проверять командой `gh pr view <номер> --json mergeable,mergeStateStatus`.
- Один PR соответствует одной задаче. Несвязанные изменения не подмешивать и выносить в отдельную task-ветку.
- Несколько задач класть в один PR только когда они являются одной механикой и по отдельности не имеют смысла. Слабо связанные задачи и большая задача с независимыми ветвями разносятся по отдельным PR, даже если делаются подряд.
- Карточка — не единица PR. Делить по поведению, которое reviewer проверяет в игре: если в одной карточке две механики, которые проверяются и откатываются независимо, это два PR.
- Ориентир при сомнении: если по задаче можно дать отдельное ревью и отдельно откатить её, она заслуживает своего PR.
- Если автор и reviewer используют один GitHub-аккаунт, GitHub не даёт сделать self-approve. В solo-flow ручная проверка владельца является достаточным процессным подтверждением, но не создаёт формальный approval.
- После успешного ревью владелец может сам выбрать в Rider `Merge Review -> Merge` либо попросить ассистента выполнить merge. Результат для Git одинаковый; разрешение ассистента владельцу не требуется.
- Отдельно сообщать ассистенту о самостоятельном merge необязательно. Перед следующей работой ассистент сам проверяет состояние PR, `origin/main` и task-веток.
- По умолчанию использовать обычный `Merge`, сохраняя фокусные коммиты. `Squash and Merge` или `Rebase and Merge` применять только по отдельной договорённости.
- Описание PR по умолчанию делить на секции «Что изменилось» и «Что проверить». Писать человеческим языком с позиции поведения игры, чтобы reviewer сразу понял суть задачи и сценарии приёмки без чтения карточки и диффа.
- В секции «Что изменилось» давать суть итогового поведения в одном-трёх предложениях. Влияющие на приёмку условия, числа, исключения и ограничения терять нельзя, но пишутся они один раз — пунктами «Что проверить»; вторая секция их не повторяет. Названия классов, конфигов, полей и формулы указывать только когда без них нельзя понять или принять изменение.
- Числа давать такими, какими их видит игрок: итоговые проценты на экране, а не приращения из конфига.
- В секции «Что проверить» перечислять только действия reviewer и ожидаемый результат. Не превращать её в отчёт ассистента о выполненной автоматической проверке.
- Успешную сборку, количество тестов, отсутствие ошибок, отсутствие ручной проверки, перечень изменённых файлов и другие служебные детали в описание PR не добавлять. Они остаются в CI, рабочем ответе ассистента или обсуждении конкретного замечания.
- Дополнительную секцию «Важно» добавлять только для реального отличия от задачи, известного ограничения приёмки, несовместимости данных или обязательной зависимости и порядка merge. Если такого комментария нет, секцию не создавать.
- В конце давать ссылку на исходную задачу и before/after media для UI, если они есть.
- В описание не писать: историю принятых решений, разбор отвергнутых вариантов, цитаты правил, таблицы «было/стало», пересказ диффа по файлам и объяснения, зачем нужен каждый фикс. Это видно в диффе и в тредах, а в таймлайне мешает читать.
- Причину правки называть одной строкой, а не абзацем. Если объяснение не влезает в строку, ему место в треде у конкретной строки кода.

## После merge

- Merge через веб-интерфейс GitHub или панель Pull Requests выполняется на сервере. Локальный репозиторий об этом не узнаёт сам: пока не выполнена синхронизация, локальный `main` отстаёт, и это нормальное состояние, а не потерянный merge.
- `fetch` обновляет только удалённые ссылки `origin/*` и никогда не двигает локальные ветки. После него мерж-коммит появляется в графе под `origin/main`, но локальный `main` остаётся на прежнем месте, пока не сделан `pull`.
- До `fetch` влитые коммиты выглядят висящими в своей task-ветке: граф рисует коммит под единственной ссылкой, которая на него смотрит.
- `pull` вливает в ту ветку, на которой стоишь. Выпадающий список в диалоге Rider выбирает источник, а не назначение: `pull origin main` с task-ветки обновит task-ветку, а не `main`.
- После мержа PR, от которого зависит другой открытый PR, дочерняя task-ветка не обновляется сама. После `fetch` в ней нужно явно влить актуальный `origin/main`, разрешить конфликты, проверить diff и запушить обновление в тот же PR; только после этого продолжать его ревью или merge. Тем же шагом убрать из описания дочернего PR ставшую неверной пометку о порядке merge.
- Панель Log с фильтром `Branch: main` показывает локальную ветку, а не `origin/main`. Сравнивать состояние после merge только по обновлённому локальному `main`.
- `fetch` и список Pull Requests — разные кэши. `fetch` обновляет git-рефы: ветки, коммиты, граф. Список PR тянется по API GitHub и обновляется отдельно — по таймеру, кнопкой Refresh или переоткрытием панели. Свежесозданный PR может не появиться в списке даже после `fetch`.
- После push в открытый PR обновлять его состояние отдельно: в Rider нажать ПКМ по любому файлу этого PR и выбрать `Refresh Pull Request`. Обычный `fetch` подтягивает только git-рефы и не обновляет кэш PR или комментариев; если карточка PR всё ещё показывает старое состояние, закрыть и заново открыть её, а затем перезапустить Rider при необходимости.
- Push в ветку открытого PR делает устаревшими все треды комментариев, привязанные к сдвинувшимся строкам: GitHub помечает их outdated и сворачивает, а панель Rider перестаёт показывать их вовсе — вместе с вопросами владельца и ответами на них. `Refresh Pull Request` это не лечит, потому что треды никуда не делись, просто скрыты.
- Отвечать на замечание только репликой в его треде, отдельным сообщением под вопросом. Общий комментарий к PR для этого не использовать: владелец читает ревью по коду, и ответ, оторванный от строки, до него не доходит.
- Комментарии владельца не удалять и не редактировать ни при каких условиях. Свои прошлые ответы тоже не подчищать: тред должен читаться целиком, вместе с тем, как менялось решение.
- Тред помечать resolved только когда вопрос действительно снят: правка внесена или решение принято и озвучено. Пока идёт обсуждение, тред остаётся открытым.
- Если тред всё же уехал в outdated, завести новый тред на актуальной строке того же места и ответить там, сославшись на устаревший. Возвращать видимость общим комментарием к PR бесполезно.
- Пока владелец идёт по PR, ассистент не пушит в его ветку без спроса: правки копятся и уходят пачкой после прохода. Иначе владелец теряет собственные вопросы из виду посреди ревью.
- GitHub автоматически удаляет remote task-ветку после merge. Ассистент при следующем действии проверяет этот результат и не ждёт отдельного напоминания пользователя.
- Ассистент автоматически удаляет локальную task-ветку сразу после подтверждённого merge либо перед началом следующей задачи.
- Перед удалением обязательно проверить, что ветка полностью влита в `origin/main` и в ней нет отдельных незамерженных коммитов. Непроверенные, открытые и содержащие уникальную работу ветки не удалять.
- После очистки обновить локальный `main` из `origin/main`. Следующую task-ветку создавать только от этого состояния.
- Порядок синхронизации после merge на сервере: `git checkout main`, `git pull --ff-only`, `git fetch --prune`, `git branch -d <ветка>`. Переход на `main` первым шагом обязателен: иначе `pull` уедет в текущую task-ветку, а удалить ветку, на которой стоишь, git не даст.
- Удалять локальную ветку строчной `-d`: она отказывается сносить ветку с неслитыми коммитами и тем страхует от потери работы. Прописную `-D` использовать только осознанно.
- Ветку, на которую смотрит base хотя бы одного открытого PR, не удалять. Удаление базы закрывает дочерний PR автоматически, и переоткрыть его GitHub уже не даёт: содержимое приходится переносить новым PR, а история ревью теряется.

## Цепочки pull request

- Стек PR мержить строго снизу вверх и по одному, проверяя результат после каждого шага.
- Перед merge родительского PR переназначить base дочернего на ту ветку, в которую вливается родитель (обычно `main`). Порядок именно такой: сначала переназначение, потом merge. После merge родителя дочерний PR уже закрыт, и чинить поздно.
- Автоудаление ветки при merge (`--delete-branch`, кнопка `Delete branch`) включать только когда на эту ветку не смотрит ни один открытый PR.
- Не мержить стек циклом или пачкой команд: каждый шаг меняет base следующего, и цикл гарантированно закрывает часть PR вместо merge.
- После каждого merge проверять, что дочерние PR остались открытыми, их base указывает куда нужно, а diff не разбух за счёт чужих изменений.
- Разбухший diff после merge родителя — не ошибка веток, а залипший указатель GitHub. Переназначение base до merge (правило выше) фиксирует не только имя ветки, но и её тогдашний коммит; после merge родителя этот `baseRefOid` сам не обновляется, и PR продолжает считать разницу от старой точки. Проявляется как сотни чужих файлов в diff при нескольких изменённых локально.
- Сверять это числом, а не глазами: `gh pr view <N> --json changedFiles,additions,baseRefOid` против `git diff --stat <base>...<head>`. Расхождение означает залипшую базу, а не лишние коммиты в ветке.
- Чинится закрытием и переоткрытием PR (`gh pr close <N> && gh pr reopen <N>`) — это заставляет GitHub пересчитать базу. Пуш в ветку и повторное назначение того же base не помогают. Ревью, треды и описание при переоткрытии сохраняются.
- Не пытаться чинить это ребейзом ветки или переносом работы в новый PR: ветки в порядке, чинить нужно указатель.
- Независимую работу не заводить в стек. Мелкая правка, не связанная с темой цепочки, идёт отдельным PR от `main` и мержится первой: её ревью занимает минуты, она не ждёт всей цепочки и не двигает базы. В стек попадает только то, что действительно стоит на предыдущем звене.
- Порядок для владельца выстраивать так же: сначала независимые PR, потом основная цепочка. Держать в стеке то, что могло быть отдельным PR, — самая дорогая ошибка планирования: правка застревает до последнего merge и на каждом шаге участвует в пропагации.
- Сразу после merge обновить локальный `main` и влить его в верхнюю ветку стека — ту, чей base стал `main`. Дальше пропагировать парами вниз: родитель -> потомок, до конца стека. Каждый шаг — отдельный merge со своим сообщением.
- `main` вливать только в верхнюю ветку. Влитый напрямую в глубокую ветку, он приносит коммиты, которых нет в её базе, и они всплывают в diff её PR как её собственная работа.
- Пропагацию не откладывать: пока она не сделана, дочерние PR висят `CONFLICTING`, а любая правка в них конфликт только наращивает.
- Правило действует и для независимого PR в `main`, который не входит в стек: если он тронул файл, который правят ветки стека (например `TASKS.md`), после его merge стек тоже пропагируется.
- После пропагации проверить у каждого PR стека `mergeable` и `mergeStateStatus`, а не только у ближайшего.
- Если PR всё же закрылся из-за удалённой базы, восстановить содержимое новым PR в `main` и явно указать в описании, какой закрытый PR он заменяет.
- Удаление базы и merge родителя — разные события. При merge родителя с включённым автоудалением ветки открытый дочерний PR не закрывается: GitHub переводит его на базу родителя. Дочерний PR закрывается в другом случае — когда ветку сносят отдельно от merge.
- Правило переназначать base вручную до merge родителя это не отменяет. Разница между случаями зависит от порядка действий и настроек репозитория, а цена ошибки — закрытый PR без права переоткрытия. Переназначение стоит секунду и уравнивает результат при любом поведении GitHub.

## Защита main в соло и в команде

- В solo-flow PR остаётся обязательным: он даёт цельный diff, историю обсуждений, автоматические проверки и точку осознанного merge даже без второго GitHub-пользователя.
- Приватность репозитория и защита `main` решают разные задачи: private скрывает исходники от посторонних, а branch protection ограничивает действия уже допущенных участников и автоматизаций. Защита ветки не делает код приватнее.
- Текущее solo-решение: не покупать GitHub Pro только ради branch protection приватного репозитория. Осознанный PR-flow и локальный `pre-push` дают владельцу удобное ревью и защиту от случайного прямого push без ежемесячной подписки; это процессная гарантия, а не серверный запрет, который невозможно обойти.
- Локальные Git hooks обязательны. Ассистент не использует `--no-verify`, не отключает `core.hooksPath` и не обходит проверки другим способом.
- Прямой коммит в `main` закрыт для ассистента правилом, а не git-хуком. Хук бьёт по тому, кто за клавиатурой: в IDE владельца он молча роняет коммит без внятного сообщения, а ассистента не держит — обход стоит один флаг. Владелец решает сам, идти ему через PR или закоммитить в `main` напрямую.
- Отсюда граница: git-хук несёт только проверки, одинаково нужные обоим, — сверку парных файлов и хуки LFS. Запреты, адресованные ассистенту, живут в `_guidelines/` и при необходимости дублируются hook'ом Claude Code в `settings.json`: он срабатывает на вызовах ассистента и не задевает владельца.
- Branch protection для private-репозитория остаётся доступным вариантом при GitHub Pro. Возвращаться к нему имеет смысл при появлении второго активного разработчика, обязательных CI-checks или требования технически исключить прямой push; в solo-flow это не обязательная покупка.
- При появлении второго разработчика protection полезен даже при полном доверии: он защищает от ошибок, требует прохождение проверок и закрепляет ревью. Включать минимум один обязательный approval от другого пользователя с write-доступом; self-approve не считается ревью.
- В личном private-репозитории GitHub collaborator получает write-доступ: отдельного более низкого read-only уровня здесь нет. Для гранулярных ролей `Read`, `Triage`, `Write`, `Maintain`, `Admin` переносить репозиторий в organization и выдавать минимально необходимую роль.
- Если человеку нельзя доверять сам код, доступ к private-репозиторию не выдавать: branch protection защищает ветку, но не мешает допущенному участнику прочитать и сохранить исходники локально.
- В командном flow дополнительно требовать успешные status checks и закрытие review conversations. Обычным разработчикам не давать bypass; административный bypass оставлять только как аварийный путь.
- Независимо от размера команды изменения ассистента проходят один цикл: task-ветка -> PR -> ревью -> исправления в том же PR -> merge -> очистка ветки.

## Зеркало на GitHub при закрытом корпоративном сервере

- Правило включается в одном случае: корпоративный git отдаёт наружу только SSH, веб-интерфейс и API закрыты. Тогда ни PR-панель IDE, ни ассистент к серверу не подключаются, и ревью по коду становится невозможным — а без него не работает весь цикл из разделов выше.
- Заводить зеркало решает владелец кода, не ассистент. Это исходники компании на стороннем аккаунте, и вопрос здесь не технический.
- Имена remote фиксированные и постоянные: `origin` — GitHub с ветками, PR и работой ассистента; `gitlab` (или имя своего сервера) — корпоративный. `origin` не переназначать под задачу: один push не туда стоит дороже, чем привычка держать два имени.
- Работа целиком идёт на `origin`: task-ветка -> PR -> ревью -> merge -> удаление ветки. Ничего в этом цикле зеркало не меняет, merge на GitHub остаётся точкой истины.
- На корпоративный сервер уходит только `main` и только после merge. Task-ветки туда не пушить: свой цикл они уже прожили, а второй PR на закрытом сервере никто не откроет.
- Синхронизация всегда в одном порядке: `git fetch gitlab`, влить его `main` в свой, если сервер ушёл вперёд, затем `git push gitlab main`, затем `git push origin main`. Сервер общий: залитое поверх чужих коммитов зеркало расходится молча, а чинится вручную.
- Перед первым push зеркала проверить общего предка: `git merge-base --is-ancestor <remote>/main main`. Не предок — истории разошлись, и push с `--force` уничтожит чужую работу.
- Держать в поле зрения квоту LFS: у GitHub бесплатно 1 ГБ хранилища и 1 ГБ трафика в месяц, и тяжёлые бинарники зеркала съедают её быстрее, чем кажется.

## Правила коммитов
Этот блок перечитывать перед каждым `git commit`.

- Перед коммитом прочитать staged diff целиком и сверить его со всеми профильными документами затронутых тем. Скриптовых проверок содержания правил нет — этот проход единственный, что их ловит.
- Коммит — одна строка заголовка и один тезис. Body не писать: объяснения, перечень файлов и подробности реализации оставлять в ответе пользователю.
- Если изменение не помещается в один тезис, разложить его на несколько фокусных коммитов.
- Сообщение создавать только через `git commit -m "<одна строка>"`. Не использовать `-F`, heredoc и несколько `-m`.
- Писать на русском, с большой буквы, глаголом в прошедшем времени: «Добавил…», «Поправил…», «Убрал…», «Вернул…», «Снизил…».
- Формулировать просто: что сделано и где. Не использовать канцелярит, технические подробности, имена классов и полей без необходимости.
- Не использовать шумные формулировки вроде `misc changes`, `temp fix`, `wip`.
- Подъём версии называть по тому полю, которое поменялось. `bundleVersion` (Player Settings -> Version) один на обе платформы и виден в сторе — «Обновил версию приложения до 1.0.7», с номером. Платформенные счётчики сборки называть без номера: `versionCode` (Bundle Version Code) — «Обновил версию Android», `buildNumber` (Build) — «Обновил версию iOS». Номер там не нужен, они растут от каждой заливки.
- Никогда не добавлять `Co-Authored-By` и любую другую атрибуцию ассистенту или инструменту.
- Не подмешивать несвязанный локальный шум (`UserSettings/*`, TMP-ассеты, осиротевшие `.meta`, чужую незавершённую работу).
- Перед PR выполнять rebase/squash только тогда, когда история не соответствует этим правилам.

## Именование веток

- Task-ветку называть `<ник владельца>/<область>-<результат>`: `alex1369/ios-launch-screen`, `alex1369/shop-screen`, `alex1369/entitas-audit`.
- Ассистент сам выбирает короткое имя после понимания цели задачи. Пользователь не обязан заранее знать будущий scope или называть ветку вручную.
- Владелец ветки определяется ником в её имени. Ассистент работает от имени этого владельца и не заменяет его префикс своим.
- Если префикс task-веток зафиксирован в инструкциях конкретного проекта, используй его. Личный префикс автора навыка не переносится автоматически в чужие проекты.
- Ник совпадает с git/GitHub. Описание писать латиницей, в нижнем регистре, через дефис; без дат, недель, спринтов, номеров коммитов и слов `new`, `test`, `tmp`.
- Если имя перестало описывать цель из-за появления несвязанной работы, это сигнал создать новую ветку, а не переименовывать смысл уже открытого PR.
- Ветки без ника (`refactor/...`, `backup-...`, `codex-...`) не создавать.
- Бэкап перед рискованной операцией делать тегом, а не веткой.
