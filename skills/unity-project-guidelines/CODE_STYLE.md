# Кодстайл (Assets/Code)

Этот документ фиксирует соглашения, которые уже используются в `Assets/Code`.

## Форматирование
- При рефакторинге и изменении поведения сохранять читаемую раскладку выражений, которые остались прежними: предикатов, callback, тернарных ветвей и вызовов. Перед push убирать из диффа отдельные правки, которые только уплотняют или перераскладывают их ради ширины строки. Правила раскладки применять к новым и содержательно изменённым выражениям. Отдельная правка раскладки допустима, когда она входит в согласованную задачу. Так ревью остаётся сосредоточено на изменениях по задаче.
- Использовать 4 пробела для отступов; табы не коммитить.
- Скобки для namespace, типов и многострочных членов ставить на отдельной строке (Allman).
- Для expression-bodied членов (свойства и методы) сигнатуру оставлять в первой строке, а реализацию всегда писать на следующей строке после `=>`. Это жёсткое правило даже для однострочной реализации; не писать выражение справа от `=>` в той же строке. Так сигнатура каждого члена стоит отдельной строкой, члены класса читаются сверху вниз одинаково, а реализация не теряется в конце длинной строки. Проверка — в `code-checks.py`; лямбды, ветви `switch` и `get`/`set` внутри свойства она не трогает:
  ```csharp
  public bool HasCoins =>
      _coins > 0;

  public int GetCoinsCount() =>
      _wallet.Coins;
  ```
- Метод пишется через `=>` для одного выражения после переноса. Допустимая структурная раскладка выражений задана в разделе «Методы». Для вложенной логики или нескольких действий использовать block body со скобками (`{ ... }`).
- Свойство, вся реализация которого — одно выражение, пишется через `=>` с раскладкой из раздела «Методы». `get { return …; }` с единственным `return` не пишется: скобки и `return` ничего не добавляют к выражению, а такое свойство выглядит не так, как соседние предикаты, и читатель ищет в нём вторую инструкцию. `get { ... }` / `set { ... }` — только когда в accessor-е больше одной инструкции. Проверка — в `code-checks.py`.
- Добавлять пустые строки между логическими секциями (`using`, поля, конструкторы, методы), но не накапливать несколько пустых строк подряд.
- Правая направляющая IDE — ориентир, а не предел длины строки. Раскладку выражений определяют правила раздела «Методы»; перенос ради ширины запрещён.
- Разрешены однострочные guard clauses без скобок, если тело состоит из одного выражения:
  ```csharp
  if (!_dialogueBackground)
      return;
  ```
- Не оставлять trailing whitespace ни в одной строке и не оставлять whitespace-only «пустые» строки: разделительная строка обязана быть по-настоящему пустой. Это относится и к строкам, которые правка только сдвигает.
- Правило про whitespace распространяется на файлы, которые пишем мы. Сериализованные Unity ассеты (`.unity`, `.prefab`, `.asset`, `.meta`, `.anim`, `.controller`, `.mat`) движок пишет сам и оставляет в них висящие пробелы; править их руками нельзя — при следующем сохранении Unity вернёт всё обратно.
- Сохранять формат окончания файла как в оригинале: если в файле не было завершающего перевода строки, не добавлять его; если был — не добавлять лишние пустые строки.

## Using-и и неймспейсы
- `using` директивы держать вне namespace.
- Порядок групп: `System` / `System.*`, project namespaces (`Code.*`), сторонние SDK, Unity namespaces, затем aliases (`using ILogger = ...;`).
- Не использовать `using static`; для конфликтующих типов использовать alias, например `using Object = UnityEngine.Object;`.
- Удалять неиспользуемые `using` при любой правке файла.

## Типы
- Один top-level тип на файл; имя файла совпадает с публичным типом.
- Не объявлять вложенные типы внутри классов/структур (`class`, `struct`, `record`, `enum`, `interface`, `delegate`). Все типы размещать только на top-level (один уровень файла/namespace). Исключение одно — данные extension-класса, оно описано ниже.
- Исключение для state-моделей: в файле state допускается второй top-level тип payload (`<StateNameWithoutState>Payload`), при этом payload размещается выше state-класса, а базовая часть имени должна совпадать.
- Исключение для extension-классов: данные, которые существуют только как вход или результат их методов, объявляются вложенными типами в самом конце extension-класса, после всех методов. Снаружи к ним обращаются через имя класса: `BroomLayoutExtensions.CoinMoveData`. Так видно, что тип принадлежит расчёту и сам по себе никому не нужен. В отдельный файл тип уходит, только когда им начинают пользоваться в обход extension.
- Файлы, которые содержат только наборы констант, именовать с суффиксом `Constants`.
- `class`, `struct`, `enum`, `delegate` использовать в `PascalCase`. MonoBehaviour/сервисы помечать `sealed` только когда наследование действительно нужно запретить.
- Акронимы и общепринятые аббревиатуры в именах типов и методов писать в верхнем регистре (`IAP`, `SDK`, `UI`, `API`), не смешивать с вариантами вроде `Iap`/`Sdk`. Идентификаторы и GUID называть в принятой проектом C#-форме `Id`/`Guid`: `ParentSlotId`, `TargetSlotId`, `UniqueId`, `Guid`.
- Интерфейсы начинаются с `I` (например, `IBackgroundIndexService`), элементы enum в `PascalCase`.
- `ScriptableObject` конфиги публиковать через Unity-атрибуты (`[CreateAssetMenu]`); сериализуемые поля оставлять `public` только когда это действительно authoring data.
- UI MonoBehaviour называть по домену без искусственных суффиксов (`Island`, `IslandAnimator`, `IslandConfig`); `Item` использовать только для повторяемых UI-элементов (карточки, кнопки, элементы списков).
- Повторяемый UI-элемент называется `<Домен>Item`, даже если весь он кликается как кнопка: `BoosterItem`, а не `BoosterButton`. Суффикс `Button` остаётся только у самого компонента-кнопки (`BoardButton`, `DealButton`), а не у элемента, внутри которого кнопка лежит. Событие нажатия у такого элемента называется `ButtonClicked`, поле с ним в родителе — `<Домен>Item` (`BroomItem`, `HammerItem`). Родительский компонент, который держит такие айтемы, называется по своей роли (`BoardHUD`), а не `<Домен>Buttons`: он не кнопка и не набор кнопок.
- Сценный компонент HUD называется `<Домен>HUD` (`LevelHUD`, `BoardHUD`, `SlotHUD`). Методы внутри называют по обновляемой части (`UpdateLocked`, `UpdateExtraTray`, `UpdateCountdown`), не повторяя `HUD` в каждом имени. Безликие `*Labels` и `*Texts` запрещены: по такому имени не видно, какую часть метод меняет, и у всех HUD они выглядят одинаково.
- Глагол `Refresh` в имени — только у ECS-системы, которая проталкивает состояние наружу (`RefreshLevelProgressSystem`). Метод того, кто принимает или перерисовывает данные, — view, окна, UI-сервиса, в том числе приватный обработчик события, — называется `Update…` по обновляемой части: `UpdateCurrentLevel`, `UpdateGems`, `UpdateContainers`. Причина: по `Refresh` читатель находит источник пуша, по `Update` — место, где его принимают; один глагол на обе роли прячет, кто кого обновляет. Редакторских инструментов, которые перечитывают кэш (как `AssetDatabase.Refresh`), правило не касается. Проверка — в `code-checks.py`.
- Entitas-компоненты обязаны использовать суффикс `Component`, если их имя совпадает с runtime-типом проекта (`MonoBehaviour`, service, config, animator и т.д.); Jenny убирает этот суффикс в сгенерированных matchers/API.
- В gameplay/meta/domain naming не использовать суффиксы `View` и `Controller`. Исключение - инфраструктурный view-layer (`IEntityView`, `EntityBehaviour`, `ViewPrefab`, registrars/bindings вокруг entity views), где термин отражает техническую границу.

## Поля и свойства
- Имя поля описывает то, что оно хранит или показывает сейчас. Если изменился смысл значения, обновить имя у получателя и в местах передачи. При переименовании сериализованного поля проверить привязки в префабах и сценах.
- Приватные поля: `_camelCase`; для зависимостей из конструктора/инжекта предпочитать `readonly`.
- `const` называть в `UPPER_SNAKE_CASE` (`PROGRESS_KEY`) при любой видимости, а `static readonly`, используемые как именованные константы, — в `PascalCase` (`ProgressKey`). Стили не смешивать: `const` в `PascalCase` и `static readonly` в `UPPER_SNAKE_CASE` не пишутся.
- Технические литералы, у которых есть смысл (индекс материала в renderer, индекс слота, размер буфера, шаг цикла), выносить в `const` с говорящим именем и не писать голым числом в вызове. Балансные и дизайнерские числа, в том числе границы механик (последний номинал, сколько выдаётся за покупку, лимиты), в `const` не зашивать: они живут в конфиге по [ARCHITECTURE_GUIDELINES.md, «Границы зависимостей»](ARCHITECTURE_GUIDELINES.md#границы-зависимостей).
- Значение, которое уже выводится из конфига (последний номинал = последний цвет палитры), брать из конфига, а не дублировать числом — ни в коде, ни в тестах.
- Порог и границу называть через `Min`/`Max` и то, что они ограничивают: `MinProgressToForceBuild`, `MaxHearts`. Слово `Threshold` в именах не использовать: по нему не видно ни направления сравнения, ни того, что сравнивается.
- Доменные типы и свойства называть нейтрально по предметной области; не использовать в доменных моделях (`GameItem`, конфиги, gameplay сущности) аналитические/трекинговые названия.
- Суффикс `Config` носит корневая модель статик-данных независимо от носителя: и `ScriptableObject`, и класс, который читается из JSON (`BoostersConfig`, `DealConfig`). Запись-сущность внутри конфига, на которую ссылаются по ключу из сейва, префаба или другого конфига, называется с суффиксом `Definition`: `IslandDefinition`, `StatusDefinition`. Остальные вложенные части конфига называются с суффиксом `Data`: `DealFillRuleData`, `RewardData`, `PriceData`. Данные прогресса игрока и прочие plain-контейнеры вне статик-данных также называются с суффиксом `Data`.
- Поле, локальная переменная и параметр, хранящие конфиг, называются полным именем своего типа в `camelCase`: `ChipNumbersConfig chipNumbersConfig`, `HeartsConfig heartsConfig`, `ChipPaletteConfig chipPaletteConfig`. Имя обязано заканчиваться на `Config`, а перед суффиксом обязана стоять доменная часть.
- Отбрасывать `Config` из имени запрещено: `_numbers`, `palette`, `number`, `color` не читаются как конфиг, и в месте использования нельзя понять, что это static data, а не доменная сущность.
- Голое `config`/`_config` тоже запрещено: когда в методе появится второй конфиг, различить их будет нечем, а по сигнатуре helper-метода не видно, какой именно конфиг он берёт.
- Исключение: параметр лямбды внутри одного выражения (`Numbers.Find(config => config.Id == id)`) — он живёт одну строку, и тип читается по самой коллекции.
- Имя коллекции обязано называть то, что в ней лежит, а не соседнее понятие. `List<BoardSlotSnapshot>` — это `slotSnapshots`, а не `slots`: сокращение до «слотов» переносит имя на другую сущность и читается как список самих слотов. Это же относится и к методу, который такую коллекцию возвращает.
- Для остальных полей, локальных переменных и параметров выбирать самое короткое имя, которое остаётся однозначным в своём scope. `_requests`, `_actions`, `_entities`, `_buffer`, `_factory`, `service`, `animator` допустимы, если тип, класс и единственный объект этой роли полностью объясняют смысл; механически повторять полное имя типа не нужно. Доменное уточнение добавлять, когда объектов одной роли несколько или без него назначение действительно теряется: `_slotBuffer` и `_chipBuffer`, `_dialogueFactory` и `_entityViewFactory`.
- Один сериализуемый параметр — ровно одна строка с объявлением. Атрибуты `SerializeField` и `Range` писать в той же строке перед объявлением. `Header` — исключение: писать его на отдельной строке непосредственно над первым параметром секции; перед каждым не первым `Header` оставлять одну пустую строку. Внутри секции пустые строки между параметрами не ставить.
- В аниматоре с несколькими эффектами общие ссылки на объекты держать сверху, а настройки каждого эффекта объединять под своим `Header`. Добавляя секцию, сверить весь инспектор, чтобы параметры соседних эффектов читались такими же группами. Так длительность, задержка и кривая видны рядом с эффектом, который они настраивают.
- `[FormerlySerializedAs]` запрещён полностью — и как атрибут поля, и в форме `[field: FormerlySerializedAs]`. Переименование сериализуемого члена доводить до конца руками: переименовать `<Old>k__BackingField` на `<New>k__BackingField` во всех `.prefab`, `.unity` и `.asset`, где он встречается, и проверить, что значения на месте. Атрибут-миграция оставляет мусор в коде навсегда ради разовой правки данных.
- Inspector-состояние сериализовать через auto-properties с `[field: SerializeField]`, чтобы сохранять инкапсуляцию:
  ```csharp
  [field: SerializeField] private Button CloseButton { get; set; }
  ```
- Для `DialogueBase`-наследников с собственными serialized fields обязательно добавлять над их блоком `[field: Header("...")]`.
- Текст `Header` для диалога писать по производному имени класса без суффикса `Dialogue` (`ReviewEntryDialogue` -> `Review Entry`, `WinStreakDescriptionDialogue` -> `Win Streak Description`).
- Если у `DialogueBase`-наследника нет собственных serialized fields, отдельный `Header` не нужен.
- Публичные изменяемые поля использовать редко; в основном в data-контейнерах (ScriptableObject, простые MonoBehaviour).
- Перед тем как назвать метод, свойство, параметр или ассет, найти, как это понятие уже называется в модуле и соседних системах (`UnlockSlotSystem`, `isSlotUnlockable` → слово `Unlock`), и взять то же слово. Новое слово — только для нового понятия, и тогда из домена, видимого вызывающему (`PlayOpen(bool withBeater)`), а не из внутренней механики или жаргона анимации (`beaten`). Слово, уже занятое другим понятием модуля, не брать: в доске `Cover` — крышка трея, поэтому флаг катсцены не `IsCoveringBoard`. Если у сервиса будут и другие сценарии, его свойства и методы называются с предметом сценария: `PlaySlotUnlock`, `IsSlotRevealPending`, а не `IsRevealPending`, про который не понять, чьё раскрытие. Свойство сервиса называет его собственное состояние его же словами (`IsRevealPending` — раскрытие в катсцене ещё впереди), а не то, что из-за этого происходит с чужим объектом (`IsBoardHidden` читалось как «доску спрятали»). Слово, которого нет ни в модуле, ни в том, что видит игрок, — придуманное, и его заменяют до push: уходящая доска — `BoardLeaving` по `PlayLeave` её аниматора, а не `BoardRetiring`; процесс смены доски — `BoardChange`, роль подготовленной входящей доски — `IncomingBoard`. Этот словарь описывает роли досок: `NextLevel`, `NextFrame` и `Id.Next` по этому примеру не переименовывают. Новые типы коммита перечисляет хук после `git commit`, и для каждого называется источник слова. Слово в имени нового типа, которого нет в коде проекта до коммита, хук перед коммитом не пропускает, пока ассистент не найдёт ему источник: модуль и его SDK, MonoBehaviour фичи, то, что видит игрок. Нашёлся — слово одобряется командой `code-checks.py --approve-word <Слово>` из папки проекта, не нашёлся — имя меняется. Владельца об отдельном слове не спрашивают: вопрос о слове без кода перед глазами ему непонятен, а имена он проверяет на ревью МР. Так `PurchaseValidation` в модуле DevToDev стал `PaymentVerification` по его `VerifyPayment`: слово `validation` пришло из таблицы ГД и источником не было.
- Публичный метод передачи данных диалогу называть по этим данным. Например, `SetSlotIdAndPriceGems`, `SetItem` и `SetBundle` читаются сразу после `Open<T>()`. Общее имя `Setup` скрывает, что именно передаётся.
- Метод и свойство, которые возвращают `bool`, называются вопросом: `Is...`, `Has...`, `Can...` (`IsSlotBusy`, `IsCoinSelectable`, `HasBroomMoves`, `CanTickTimer`). Утвердительная форма (`SlotIsBusy`, `MoveIsValid`, `BoardHoldsGoalCoins`) не используется. `Try...` с `out`-параметром остаётся как есть.
- Когда вызывающий различает несколько взаимоисключающих исходов без дополнительных данных, вернуть одно значение `enum`. В `Try...` результат `bool` показывает успех, а `out T` содержит данные успешной операции. Имя метода и имена результатов в месте вызова должны показывать, какое решение принято и что несут данные. Обычные исходы с разными эффектами показывать явными ветками рядом с их действиями, чтобы для чтения сценария не приходилось сопоставлять `bool` и пустой `out` из другого метода. В обработке клика по доске видно, когда создать промах, когда пропустить клик для кнопки и когда создать клик по найденному слоту.
- Условие из двух и больше проверок, собранное только из полей, свойств и сервисов класса — всего, что известно до входа в метод, — выносится в приватное свойство с именем-вопросом: `CanShowDialogue`, `CanDeal`, `CanTickTimer`. Метод тогда читается как сценарий («нельзя показать окно — выходим»), из чего складывается «можно», видно в одном месте, и условие, нужное в двух местах, не расходится между ними (`CanDeal` в `BoardHUD` и для кнопки, и для нажатия). Внутри метода остаётся условие, части которого рождаются в нём: локальная переменная, параметр, сущность из цикла (`sourceSlot.Id == animatingMove.FromSlotId`) — в свойство его не вынести, и это сам шаг метода. Одиночную проверку также оставлять внутри метода. Вводить локальное имя, когда оно переводит техническое выражение в понятие сценария. Например, `bool hitCanvas = topHit.module is GraphicRaycaster` объясняет ветку без знания класса Unity. Соседние технические проверки называть в одном словаре сценария, когда имя проясняет ветку. В разборе клика так читаются `hitCanvas` и `hitClickTarget`. Если выражение уже читается в месте проверки, оставлять его в `if` без промежуточной переменной или отдельного метода. Вынос условия в свойство проверяет `code-checks.py` по источнику частей условия.

## Комментарии
Перед коммитом любой правки проверять diff на добавленные комментарии. `code-checks.py` блокирует новые комментарии в индексированном C#-коде проекта, включая Editor. Существующие комментарии, сгенерированные файлы, сторонние плагины и файлы тестов не входят в эту проверку.

- Комментариев в коде нет: ни `//`, ни `/* */`, ни `/// <summary>`. Мы не пишем документацию. Код объясняет себя понятными именами, короткими методами и местом в архитектуре.
- Пересказ логики, причина правки, история бага и ссылка на источник — не комментарий в коде. Если это важно, место ему в описании PR.
- Если строку хочется пояснить, сначала переименовать сущность, вынести условие или выделить метод. Комментарий не заменяет рефакторинг.
- Проверка разрешает `// Command + G` в строке `MenuItem` с хоткеем `%g` и `// Has execution order to start before every other script` перед объявлением `SwitchToEntrySceneInEditor`. Новое неизразимое кодом требование движка, платформы или SDK согласовать с владельцем и добавить точечным исключением. В тестах допустимы секции `// Arrange`, `// Act`, `// Assert`.
- Сомнение, подходит ли случай под исключение, означает, что не подходит.
- Существующие комментарии в легаси попутно не удалять: чистку решает владелец. Новых не дописывать.

## Порядок членов класса
- Использовать единый порядок членов внутри класса/структуры:
  1. `const` и `static readonly` поля.
  2. События (`event`) (public -> protected -> private).
  3. Свойства.
     Это относится и к `private` member'ам: даже private/computed properties размещать выше private fields.
     Сериализуемые свойства `[field: SerializeField]` — это поля инспектора: их блок идёт первым в секции свойств, выше обычных свойств, независимо от видимости (`DebugStepper`: сначала `ValueText` и кнопки, ниже `Value`). Вычисляемое private-свойство над ними — то же нарушение: открыв класс, читатель первым видит, что настраивается в инспекторе. Проверка — в `code-checks.py`.
  4. Поля (`[SerializeField]`/public/protected/private).
  5. Конструкторы.
  6. `Construct(...)` с `[Inject]` или вызываемый создателем объекта, за ним `Set...`, которым создатель один раз передаёт данные, колбэки или зависимости до начала работы (если есть).
  7. Колбэки Unity (`Awake`, `OnEnable`, `Start`, `Update`, `OnDisable`, `OnDestroy` и т. д.) в порядке выполнения.
  8. Методы подготовки (`Initialize`, `SubscribeUpdates` и аналогичные init-методы).
  9. Методы, реализующие интерфейсы.
  10. Остальные public методы, в том числе `Set...`, который зовут по ходу работы.
  11. Методы очистки (`CleanUp`, `Dispose`, `Unsubscribe` и т. п.).
  12. Protected/internal/private методы.
  13. Обработчики подписок (`On...`) размещать в самом низу файла, в порядке подписки: сначала кнопки, затем события сервисов.
- Порядок методов повторяет жизнь объекта. Сверху стоят точки входа извне: получение зависимостей и стартовых данных (`Construct`, разовый `Set...` создателя) и вызовы движка (колбэки Unity). Ниже рамка работы: подготовка (`Initialize`, `SubscribeUpdates`), публичные действия, очистка (`CleanUp`, `Dispose`, `Unsubscribe`). Внутренние методы и обработчики идут после рамки. Место метода жизненного цикла задаёт его роль, а не видимость: `public`, `protected`, `protected override`, `private` и реализация интерфейса стоят на одном месте. Исключение — блок контракта базового класса, о нём ниже. Поэтому схема одна для окна, где `Initialize` вызывает база, и для HUD, где `Start` вызывает приватный `Initialize`. Связь видна в теле колбэка. Разовый `Set...` создателя продолжает `Construct`: объект получает всё нужное до начала работы, поэтому метод стоит сразу за `Construct`, выше колбэков Unity. `Set...`, который зовут по ходу работы, — обычный публичный метод внутри рамки. Роль определяй по месту вызова: `code-checks.py` её не различает. `BuyTrayDialogue`: `Construct`, `SetSlotIdAndPriceGems` (зовёт система открытия окна, данные читает `Initialize`), `Initialize`, `SubscribeUpdates`, `CleanUp`, обработчики. `Toggle`: `Construct`, `SetActions` (окно настроек передаёт колбэки один раз), `Initialize`, `SetState` (зовут на каждом переключении), `CleanUp`, обработчики. `BoardHUD`: `Construct`, `Start`, `OnDestroy`, `Initialize`, `CleanUp`, вспомогательные методы, обработчики. Overrides обработчиков подписок `On...` остаются в секции обработчиков внизу. Роль `On...`-метода определяй по объявлению интерфейса и месту вызова.
- Базовый класс, который объявляет контракт для наследников, держит свои `protected virtual`/`abstract` точки расширения одним блоком в порядке вызова после своего публичного API. Наследник видит весь контракт в одном месте, а момент вызова каждой точки показывают колбэки Unity базы выше. `DialogueBase`: `Construct`, `Awake`, `Start`, `Update`, `OnDestroy`, `Show`, `Hide`, `Close`, `OnClosed`, блок `OnAwake`, `Initialize`, `SubscribeUpdates`, `OnUpdate`, `CleanUp`, затем `SetCloseButtonVisible` и обработчики. `override` в наследнике и собственные методы любого класса идут по общей схеме. Место объявленных классом `protected virtual`/`abstract` методов `code-checks.py` не проверяет.
- После `Initialize`/`SubscribeUpdates` держать методы, реализующие интерфейсы, одним блоком перед остальным публичным API. Так точки входа по контрактам видны рядом. Правило относится к явным и неявным реализациям, в том числе к `OnPointerDown` из `IPointerDownHandler`. Методы интерфейса, относящиеся к жизненному циклу, например `IDisposable.Dispose`, остаются в своей секции. Место свойств и событий задают их секции. `code-checks.py` проверяет порядок стандартных методов жизненного цикла и известных колбэков в прямых наследниках `MonoBehaviour` и окон (`DialogueBase`, `ScreenBase`, `BaseWindow`). Блок реализаций сверять по декларациям интерфейсов.
- Между секциями оставлять пустые строки, чтобы структура читалась сразу.
- Внутри блока `const` / `static readonly` сначала всегда размещать все `const`, ниже — все `static readonly`.
- Между последней `const` и первой `static readonly` всегда стоит ровно одна пустая строка-разделитель. Это два разных блока, слипаться они не должны никогда.
- Для интерфейсов обязательно разделять пустой строкой блоки `event`, свойств и методов.
- В интерфейсе свойства внутри своего блока идут подряд, без пустых строк между ними. В классе наоборот: между свойствами всегда стоит пустая строка, каждое свойство — отдельный блок. Блок `event` в классе, как и в интерфейсе, остаётся слитным.
- Свойства класса внутри своей секции располагать по видимости: `public`, затем `protected`/`internal`, затем `private`. Публичное свойство не оставлять посреди блока приватных computed properties.
- Для `private`/`protected` helper-методов внутри одной секции соблюдать порядок по call-flow:
  - сначала держать единый блок `public` методов, а весь `private`/`protected` call-flow располагать уже после него;
  - внутри `private`/`protected` секции группировать методы по веткам: метод-вызыватель, сразу под ним его helper-методы, затем helper-методы этих helper-методов и так далее вниз по цепочке;
  - к следующей независимой private-ветке переходить только после того, как текущая ветка полностью размещена целиком;
  - порядок самих верхнеуровневых private-веток выбирать по читаемости и связанности private-секции, а не пытаться механически повторять порядок `public` методов;
  - utility-методы без собственной ветки (`LeftToRightSide`, small converters/checkers) размещать в самом низу этой секции.
  - правка класса включает сверку порядка методов с этим правилом, даже если в `main` он уже был нарушен: маленький дифф — не причина оставлять порядок. Checker, который зовут несколько веток, — utility и уходит вниз.

## Методы
- Всегда явно указывать возвращаемый тип (`void`, `int`, и т.д.); `var` для сигнатур не использовать.
- Тело метода примерно в 35 строк и больше — повод на ревью проверить его смысловые шаги и выделить самостоятельные расчёты, подготовку данных или применение результата, если это делает основной сценарий понятнее. Это ориентир, а не жёсткий лимит: цельную операцию не дробить ради числа, строки, скобки и смысловые разделители не уплотнять. В ECS соблюдать [видимость сценария в `Execute()`](OPTIONAL_ENTITAS.md#системы).
- Имя helper-метода должно отражать его существенные эффекты. Метод подписки/отписки работает с событиями; запуск анимации и звука остаётся отдельным явным шагом сценария. Не объединять эти действия под именем вроде `StopWaitingForVideo`: по вызову отписки читатель не ожидает запуска анимации. Если общий блок нужен нескольким вызывающим, его имя и границы всё равно обязаны соответствовать действию.
- Технические действия Unity/API добавлять по конкретному контракту и lifecycle, а не по привычке. При одинаковом требуемом поведении брать уже принятый командой подход к аналогичному сценарию в проекте или указанном владельцем соседнем проекте: единообразие упрощает чтение и поддержку. Другой подход выбирать ради конкретной пользы для текущего сценария, подтверждённой контрактом API или проверкой поведения; различие скрытых промежуточных значений без влияния на требования и предполагаемая выгода сами по себе не основание. Пауза, сброс состояния и повторная инициализация решают разные задачи: перед `enabled`, `Rebind`, `Update(0)`, сменой скорости или настройкой событий определить, какой эффект нужен и кто им владеет. Например, `sendFrameReadyEvents` требуется для `frameReady` и отключается после использования, а возобновление анимации при уничтожении окна не требуется. Обработчики должны быть готовы до момента, когда источник может отправить событие; отключение источника и отписку согласовывать с его контрактом и владельцем.
- Для dependency injection использовать конструкторы или `[Inject] private void Construct(...)`.
- `LazyInject<T>` не использовать.
- Полевая инъекция (`[Inject]` на поля/свойства) запрещена.
- Если используется method injection, применять только `[Inject] private void Construct(...)` (без альтернативных имен и без дополнительных DI-методов).
- Однострочный метод, который вызывается в одном месте, не заводить: вызов пишется прямо там. Отдельный метод обещает логику сложнее одной строки, и обёртка над одним вызовом, например переходом `_stateMachine.Enter<...>`, только заставляет в неё заглядывать. При рефакторинге проверять: если у метода осталась одна строка и один вызов, встроить его.
- Не выносить в отдельный метод короткую цепочку из двух-трёх вызовов только потому, что она повторяется в нескольких обработчиках. Звук и вибрация по нажатию кнопки пишутся прямо в каждом `On...Click`, а не в `PlayButtonFeedback()`. Метод-обёртка над парой вызовов не убирает логику, а только прячет, что именно происходит по клику. Выносить стоит расчёт, ветвление или повторяемую последовательность с собственным смыслом.
- Если callback не принимает аргументы и только вызывает один метод, использовать `method group` (конверсия группы методов) вместо пустой лямбды: `onDone: SomeMethod` вместо `onDone: () => SomeMethod()`.
- Делегаты событий и колбэки вызывать через `?.Invoke(...)`, чтобы в месте вызова было видно уведомление подписчика. Одноразовый колбэк, сохранённый в поле, скопировать в локальную переменную и очистить поле до вызова. Тогда повторный вход не вызовет его дважды.
- Колбэк, который вызывается по завершении операции, называется `onComplete`, с результатом — `Action<T> onComplete`. Своё имя такому колбэку (`onDone`, `onRequested`, `onShown`, `onChecked`) не придумывать. Отдельное имя бывает только у колбэка, который вызывается не всегда: `onSucceeded` — только при успехе.
- Порядок параметров метода: сначала объект, над которым он работает (`this` у extension), затем конфиги, затем значения окружения (язык, время), флаги `bool` в конце. Пример: `Validate(this ProgressData progress, IslandsConfig islandsConfig, SystemLanguage systemLanguage, DateTime nowUtc, bool initialVibration)`.
- Для declaration методов/конструкторов/делегатов параметры можно переносить вертикально, по одному на строку. Это относится только к месту объявления сигнатуры в классе/интерфейсе.
- Обычный вызов метода или конструктора, присваивание и простое выражение после `return` или `=>` записывать в одну физическую строку. Длинная строка, в том числе за направляющей IDE, допустима. Если выражение трудно прочитать, упростить самостоятельные вычисления и дать значениям понятные имена; не разносить аргументы по строкам и не вводить тип или метод-обёртку только ради ширины.
- Перенос по смысловой границе допустим: тело callback после `=>`, законченные операнды простого `bool`-предиката после `=>` или `return`, условие и две ветви тернарного выражения. Это разделяет самостоятельные части для чтения, а не подгоняет строку под ширину. Для многострочного предиката использовать одну законченную проверку на строку и одинаковый `&&` или `||` в конце строки; для тернарного выражения — законченное условие, затем полную ветвь с `?` и полную ветвь с `:`. Однострочная форма также допустима: каждый короткий предикат или тернарное выражение раскладывать не требуется. Внутри проверки, ветви или callback обычные вызовы и их аргументы не разрывать.
- Структурная раскладка сохраняется: блоки callback, инициализаторы объектов и коллекций, цепочки entity/tween builder и весь Entitas matcher composition, включая внешний `GetGroup(...)` и присваивание. Если `AllOf(...)` или `NoneOf(...)` содержит больше одного matcher-компонента, раскрывать состав вертикально, по одному matcher-у на строку. В обычном вызове внутри такого блока аргументы всё равно остаются одной строкой.
- Вычисляемый аргумент, который сам по себе отдельный шаг (индекс, случайный выбор, результат другого вызова), выносить в локальную переменную с именем, а не вкладывать в индексатор или аргумент другого вызова: `int prefabIndex = _randomProvider.Range(0, prefabs.Count);`, затем `InstantiatePrefabForComponent<Cutscene>(prefabs[prefabIndex])`. Короткое выражение, которое читается одним взглядом (`values[Range(0, values.Count)]` как всё тело метода), так и остаётся.
- Именованные аргументы в местах вызова по умолчанию не использовать. Считать их запрещёнными, кроме действительно редких исключений, когда без них вызов становится неоднозначным или теряет смысл из-за неочевидного литерала (`true`, `false`, `null`, числа без контекста).
- Не добавлять null-check и null-propagation (`?.`, `??`) для serialized fields, injected dependencies и config data ни в одном методе. За ссылки отвечает настройка: отсутствующая ссылка — setup error, и он должен падать сразу. Guard на `null` ставить только при реальной runtime-неопределённости, когда значение законно отсутствует во время работы.
- После присваивания параметра в поле или свойство по умолчанию продолжать работать с исходным параметром, а не с только что присвоенным членом класса.
- Исключение: если дальнейший порядок действий явно зависит от уже обновлённого состояния объекта/сервиса, после присваивания работать именно через поле/свойство. Такой код должен визуально подчёркивать причинно-следственную связь: сначала обновляем состояние (`CurrentScreen = screen`), потом выполняем действия, завязанные на это состояние (`CurrentScreen.Initialize()`).
- Не оставлять неиспользуемый код: публичный метод конфига или сервиса без единого вызывающего, приватный helper без вызова, локальную переменную без чтения, параметр конструктора без присваивания. Такой код удалять в том же изменении, где он стал лишним.
- Это правило про код, ставший лишним навсегда. На код и ассеты временно выключенной механики оно не распространяется: см. [AI_COLLABORATION_GUIDELINES.md, «Временно отключённые механики»](AI_COLLABORATION_GUIDELINES.md#временно-отключённые-механики).
- Не добавлять API «про запас»: метод заводить в момент появления первого вызывающего, а не заранее рядом с похожим.
- Подписки и listeners, установленные в `Initialize` или `SubscribeUpdates` на время жизни окна, снимать симметрично в штатном `CleanUp`. `Hide` допускает повторный `Show` на том же экземпляре. При скрытии останавливай только работу текущего показа, которую требуется отменить. Например, у видеоплеера можно отключить отправку кадров на время ожидания следующего показа, оставив делегаты подписанными.
- В `override`, который расширяет реализацию базы, вызывай `base.Method(...)` первым действием. Отступай от этого порядка только если контракт базового метода требует сначала завершить конкретное действие наследника. Например, `base.Hide` меняет `Shown`, запускает закрытие и при мгновенном скрытии может синхронно вызвать `onHidden`. До `base.Hide` должны завершиться только действия, на результат которых рассчитывает этот синхронный вызов. Для `DialogueBase.Hide` проверка в `code-checks.py` ловит вызов базы после простой последовательности вызовов или присваиваний без управляющих конструкций.
- При очистке своих частей владелец сначала останавливает независимый аниматор, затем снимает подписки и освобождает остальные ресурсы. Guard относится только к проверяемому ресурсу. В `Mascot` состояние видеоплеера не влияет на очистку аниматора. `CleanUp` аниматора безопасен до запуска эффекта. Действия, которым нужна завершённая очистка, выполняются после вызова базы и своих шагов очистки. Для штатной остановки конкретного эффекта используй существующий `Stop...`. Перед заменой или очисткой сохранённого tween используй существующий helper, который останавливает tween и обнуляет ссылку владельца (например, `Kill(ref tween)`). Если callback нужен только для присваивания `null`, достаточно этого helper. Проверка `IsPlaying` отвечает на вопрос о воспроизведении, поэтому отмену задержанного или приостановленного tween ею не ограничивай.
- Предпочитать guard clauses, чтобы уменьшать вложенность.
- Сначала проверять известные условия, которые позволяют пропустить работу. Raycast, запрос или расчёт выполнять после этих проверок и только в той ветке, где нужен результат. Условия, которым нужен результат операции, проверять после неё.
- Если несколько подряд guard clauses выполняют одно и то же действие (`return`, `return false`, `continue`, `break`, `throw`), по умолчанию объединять их в один `if` через логические операторы или в один доменный предикат. Раздельные guard-ы с одинаковым выходом оставлять, только когда каждое условие закрывает свой смысловой этап и так действительно читается лучше.
- Заголовки `if`, `else if`, `while`, `do ... while`, `for` и `foreach` от ключевого слова до закрывающей скобки записывать одной физической строкой. Для сложной проверки сначала назвать самостоятельные вычисления или составные факты, затем использовать их в коротком заголовке. При вынесении проверок сохранять короткое замыкание `&&`/`||`: вызов или чтение, которое зависело от левого операнда, не вычислять заранее без этой проверки.
- При упрощении циклов сохранять момент и число вычислений: условие `while`/`for`, приращение и вызов с побочным эффектом нельзя один раз вычислить перед циклом вместо повторной проверки. Запрос выборки `foreach`, который и так вычислялся один раз, можно подготовить перед обходом.
- Цепочка создания сущности читается как один шаг. Отделяй её пустой строкой от предыдущего самостоятельного шага. Подготовку значений, которые нужны только для создания сущности, держи рядом с цепочкой. Последующие изменения состояния отделяй от цепочки одной пустой строкой и держи вместе.
- В теле метода блоков обычно два-три, а не по одному на строку. Прежде чем ставить пустую строку, ответить, какая законченная мысль на ней кончилась; нет ответа — строка лишняя.
- Критическая последовательность, которая обязана отработать в одном кадре подряд, пустыми строками не разрывается: создание сущности цикла и изменения состояния, ради которых цикл заведён, пишутся вплотную. Разрыв читается как «между этими шагами можно вклиниться», а вклиниваться там нельзя.
- Вызов собственного метода не ставить между однородными построчными операциями над сущностями: он идёт до или после такой группы. Смешанный список читается как одна последовательность, хотя один его элемент разворачивается в отдельный сценарий. Образец — `RestartLevelState.Enter`: сперва свои методы, потом вызовы сервисов. Пустой строкой от группы он при этом не отделяется — блоки внутри одного сценария разделяются по общему правилу ниже, а не по факту вызова.
- Блок из двух строк и меньше пустых строк внутри не содержит: тело метода, `for`, `foreach`, `while`, `if`, `else`, `using`, `lock`. Две строки читаются одним взглядом, и разрыв внутри них делит то, что делить не на что. Пустая строка появляется с третьей строки тела и только там, где на ней действительно кончилась законченная мысль. Тела типов сюда не относятся: там разделение членов пустой строкой задано отдельными правилами выше.
- Самостоятельный блок `if` отделяй одной пустой строкой от соседних шагов на том же уровне. Получение значения и его немедленную проверку, подготовку аргумента и вызов с ним держи рядом. При сокращении метода сохраняй смысловые разделители и выноси цельный шаг.
- Локальную переменную заводить только когда она сокращает выражение или даёт имя тому, у чего его нет. Переменная, которая просто повторяет свойство под другим именем (`bool showsOwnStatus = slot.isExtraTraySlot;`), запрещена: читателю приходится держать в голове два имени одного факта. Именовать имеет смысл составное условие целиком, а не его слагаемое.
- Полем держать сам конфиг, а не значения, вынутые из него: `_coinUnlockConfig.MaxInitiallyUnlockedNumber` читается в месте использования, а не копируется в конструкторе в `_maxInitiallyUnlockedNumber`. Копия прячет источник и множится с каждым значением, которое понадобится классу. Расчёт по конфигу, который нужен в одном месте, делается прямо там, локальной переменной. Поле с результатом расчёта заводят в конструкторе, только когда результат нужен в нескольких местах или расчёт длинный (текст, собранный из конфига; объединение двух списков). Такие расчёты идут в конструкторе отдельным блоком после присвоения зависимостей, через пустую строку. Поле «ради одной строки в `Execute`» читается как скрытая настройка системы.
- Возврат фабрики или сервиса не продолжать вызовом в той же строке: `Open<T>()`, `Create<T>()` и подобное сначала кладут в локальную переменную, а работа с результатом идёт следующей строкой. Цепочка прячет, что объект вообще создан, и ломает точку останова.
- Если метод делает одно действие над несколькими объектами — часть по одному, часть циклом, — цикл идёт первым, а одиночные вызовы — после него одной группой: `PreloadLobbySounds` сначала подгружает список клипов, потом отдельные клипы. Цикл в хвосте метода читается как добавленный после, хотя это тот же шаг.
- Порядок строк в системе задаёт смысл действия, а не шаблон: каждая строка стоит в том шаге, к которому относится. Действие системы — то, что она сама меняет в данных, и реакция, которую игрок видит в тот же момент (катсцена, звук, закрытие окна по результату). Запрос на сохранение фиксирует именно это действие и стоит сразу за ним, отдельным блоком. То, что действие запускает дальше в других системах (рестарт уровня, метла, режим выбора цели), — уже следующий шаг со своими изменениями и своим сохранением: он идёт после запроса на сохранение отдельным блоком и в связку «изменили — сохранили» не входит. Перед строкой спросить, к какому шагу она относится. Буквальное «сохранение последним» ставило рестарт уровня между покупкой жизней и её сохранением.
- Системы с одной логикой пишутся одинаково: покупка трея, его бесплатное открытие и активация трея бустера отличаются только своими данными.
- Блок, который отдаёт данные объекту, пишется в порядке «значения → получатель → вызовы» одним куском, без пустых строк: сначала локальные значения, вычисленные из данных, затем объект, которому их отдают, затем вызовы с этими значениями. Значения из данных от получателя не зависят, поэтому идут первыми, а получатель стоит вплотную к своим вызовам: `bool countdownVisible = …;`, `BoardSlot boardSlot = board.BoardSlots[…];`, `boardSlot.HUD.UpdateExtraTray(…);`, `boardSlot.HUD.UpdateCountdown(countdownVisible, …);`. Пустая строка между подготовкой и использованием рвёт одну мысль надвое.
- Пустая строка внутри метода отделяет одну законченную мысль от другой, а не строки друг от друга. Две подряд идущие строки, где вторая работает с результатом первой, — это одна мысль, и разрывать её нельзя: `GameEntity slot = CreateSlot(board, slotIndex);` и `CreateCoins(slot, ...)` пишутся вплотную. Правило не про `return`, оно про любое место в теле метода, включая тело цикла и ветку `if`.
- Проверка простая: если убрать первую строку, вторая перестанет компилироваться или потеряет смысл — значит это одна мысль и пустой строки между ними нет.
- Перед `return` и `yield break` оставлять одну пустую строку, если в текущем методе/ветке больше двух исполняемых строк.
- Исключение: если метод/ветка по сути состоит только из двух строк, где первая что-то делает, а вторая сразу `return` или `yield break`, дополнительную пустую строку перед ними не ставить. Частый случай — фабрика «загрузить префаб → вернуть экземпляр»: две строки вплотную. Старый код с пустой строкой в таком месте (`BalloonHintFactory`) — не образец: копия переносит ошибку в новый файл, поэтому при копировании блок сверяется с правилом, а не с источником. Обе стороны правила проверяет `code-checks.py`.
- Строки считаются по экрану, а не по инструкциям. Если `return` или строка перед ним занимает несколько строк — инициализатор объекта или цепочка builder-а, — это уже не «две строки», и пустая строка перед `return` нужна: `AsSavedEntity` (`return new EntitySnapshot { … }`), `CreateCoin` (`return CreateEntity.Empty()…`). Причина та же, что у всего правила: многострочный `return` читается отдельным блоком, и без пустой строки он слипается с подготовкой. Если `return` — единственная инструкция блока (`return booster switch { … }`), пустой строки нет: ставить её некуда.
- Новые объявления дописывать в конец списка: компонент в файле компонентов, поле в классе, константу в generated-lookup, где индекс позиционный, привязку в инсталлере (и в тестовом тоже), строку в любом методе из однотипных вызовов. В начало и в середину не вставлять, даже если так меньше конфликтов при слиянии: конфликт двух строк, дописанных в конец, решается оставлением обеих, а вставка сверху переписывает историю порядка, по которой читается, что появилось раньше. Сортировки по алфавиту нет. Соседство «по смыслу» — не повод вставить в середину: сервис магазина не ставится рядом с сервисом сердец, а конфиг магазина — рядом с экономикой, он дописывается в конец каждого списка (константа пути, поле, геттер, загрузчик). Привязку в середине метода инсталлера ловит `code-checks.py`.
- К системам внутри feature это не относится: там место определяет порядок исполнения, а не история добавления. Система встаёт в ту фазу, где обязана отработать, даже если это середина файла.
- Для сериализуемого поля-коллекции в `ScriptableObject` инициализатор `= new()` не писать: Unity сама создаёт пустую коллекцию при загрузке ассета. Инициализатор оставлять только там, где объект собирает не Unity: JSON-конфиги, обычные классы, `ProgressData`.
- Порядок гарантируется архитектурой, а не проверками. Не писать защитные `if` вида «а вдруг уже создано», «а вдруг ещё не готово», «а вдруг вызовут второй раз». Если такая проверка понадобилась, это сигнал, что неверен порядок инициализации или время жизни владельца; чинить нужно порядок, а не добавлять guard.
- Не закладывать заготовки под будущие миграции формата данных. Формат меняем — чиним по факту изменения, а не заранее.
- Не добавлять fallback-логику между конфигом и runtime-сервисом “на всякий случай”. Если значение обязано приходить из конфига, сервис должен возвращать его напрямую; проблемы править в конфиге, а не маскировать дополнительными проверками.
- Ошибки не прячем. Если данные или состояние сломаны, код падает громко: мы первыми видим это при разработке и в тестах, и до игрока оно не доходит. Тихая подмена там, где значение обязано быть (`return 0`, `return default`, `return false`, `null`, пропуск через `continue`), хуже падения: баг уезжает в релиз незамеченным. Существующие `throw` и `IExceptionProvider` и есть этот громкий сигнал — при чистке кода их не удалять и не заменять тихим возвратом.
- Для конечного набора режимов использовать `switch`: выражение, когда каждая ветка даёт значение, и оператор, когда ветки выполняют действия.
- Исключения бросать через `IExceptionProvider`, если он доступен; иначе использовать стандартные framework exceptions (`ArgumentException` и т.д.).
- Пустой `catch` пишется только с конкретным типом ожидаемого исключения и без комментария: `catch (OperationCanceledException) { }`. Тип сам говорит, что гасим осознанно, и IDE перестаёт просить комментарий.
- Общий `catch { }` или `catch (Exception) { }` с пустым телом и пометкой «ignore» не писать. Если внутри `try` нечему бросать, убрать `try` целиком; если ошибка ожидаема, назвать её тип.

## Коллекции и аллокации
- Для рабочего буфера, который заполняет вызываемый API, использовать обычный `List<T>` у владельца буфера и передавать его напрямую. `IReadOnlyList<T>` использовать, когда на границе нужно предоставить коллекцию владельца только для чтения, как список клипов аудиосервиса. Для промежуточного результата внутри одного сценария сохранять существующий тип коллекции без лишних копий и обёрток.
- Коллекции создавать с явным типом (`new List<DialogueBase>()`) или target-typed `new()`, если тип переменной очевиден:
  ```csharp
  private readonly List<EventTrigger.Entry> _entries = new();
  ```
- Локальные переменные объявлять с явным типом; `var` не использовать.
- При создании объекта через присваивание не переносить `new` на отдельную строку само по себе.
  Предпочтительный формат:
  ```csharp
  SomeService service = new SomeService(dependencyA, dependencyB);
  ```
- При присваивании результата вызова применять правило одной физической строки из раздела «Методы».
  Предпочтительный формат:
  ```csharp
  ReviewFeedbackDialogue dialogue = DialogueService.Open<ReviewFeedbackDialogue>(DialogueOpenMode.PushClosePrevious);
  ```
- Использовать существующие helper extensions (`ForIntCountedItem`, `SetState` и т.д.) вместо копирования логики.

## Паттерны Unity
- Подписки MonoBehaviour на кнопки и события делаются в `Start`, снятие — в `OnDestroy`. Если шагов больше одного, `Start` и `OnDestroy` вызывают пару `Initialize`/`CleanUp` (`BoardHUD`); одну подписку пишут прямо в `Start` (`BoosterItem`, `TextShadow`), обёртка ради одной строки не нужна. Причина: подписки всех view лежат в одном месте и снимаются симметрично, читатель не ищет их по разным методам жизненного цикла. `Awake` в объектах игры не пишем: он срабатывает внутри `Instantiate`, и по коду заказчика не видно, что объект уже что-то сделал. Подготовку, без которой объект нельзя использовать сразу после создания, делает `Initialize`, который зовёт фабрика (`CutsceneFactory`, `MascotFactory`); предзагрузка (`VideoPlayer.Prepare`, звук) — тоже в нём. Существующий `Awake` у `DialogueBackground` и базы окон — старый код, по нему новый не пишется. Окна (`DialogueBase`) живут по своему циклу `Initialize`/`SubscribeUpdates`/`CleanUp`, его вызывает база. Новый `Awake` ловит `code-checks.py`.
- Перед исправлением существующего view проверить его текущее поведение, базу, владельца создания/закрытия и ближайший рабочий аналог той же роли. Сохранять рабочий контракт, пока не найден конкретный сценарий, который требует его менять. Например, `CurtainIntroAnimator` сохраняет `Start` для собственной настройки и `Update` для ручного шага tween. Перенос в сервис или coroutine меняет момент вызова и требует причины. `Initialize` от фабрики или владельца нужен, когда тот должен получить готовый объект до первого использования. Независимая настройка не создаёт такой зависимости. Готовый diff из другой ветки, тега или от другого агента проходит ту же сверку.
- Наследник базового окна (`DialogueBase`, `ScreenBase`, `BaseWindow`) использует предусмотренные базой `Initialize`/`SubscribeUpdates`/`CleanUp`. Не объявлять в нём собственные `Awake`, `OnEnable`, `Start`, `Update`, `LateUpdate`, `FixedUpdate`, `OnDisable`, `OnDestroy` и не обходить этот запрет через `OnUpdate`: жизненным циклом уже владеет база, а закрытие окна и деактивация GameObject — разные действия. Подписки, добавленные в окне, снимаются его штатным `CleanUp`, а не отдельным `OnDisable`. Владельца покадровой работы определяет [ARCHITECTURE_GUIDELINES.md, «Порядок выполнения»](ARCHITECTURE_GUIDELINES.md#порядок-выполнения). Новые колбэки у прямых наследников блокирует `code-checks.py`.
- По умолчанию диалог подготавливается в `Initialize`: штатный `Open<T>` создаёт экземпляр, а `Close` его уничтожает. Повторный вход через `Open<T>` снова проходит инициализацию. Если игре нужно показать тот же экземпляр, проследи конкретный путь от вызывающей фичи до скрытия и возврата окна и проверь существующие точки входа. Расширяй жизненный цикл общей базы только при доказанной потребности этого сценария, когда текущих точек входа недостаточно.
- Для разового визуального действия по событию готовности Unity/SDK подписаться на это событие в штатной точке инициализации и снять подписку в штатной очистке. Не добавлять ради того же события покадровый опрос, флаг ожидания, произвольный таймаут с запасным сценарием или ручной `Animator.Update`/`Rebind` для маскировки неверного порядка либо подгонки теста. Реальный таймаут должен следовать из требования или контракта операции и исполняться у её существующего владельца.
- Корутины и ожидания в async-коде пишутся по [STATE_FLOW_AND_ASYNC.md](STATE_FLOW_AND_ASYNC.md): «Граница корутин» задаёт владельца корутины и имя метода, «Инструменты асинхронности» — чем ждать.
- Platform-dependent код оборачивать в preprocessor directives с корректными отступами:
```csharp
#if !UNITY_EDITOR && (UNITY_ANDROID || UNITY_IOS)
    _notificationPermissionService.OpenAppSettings();
#endif
```
- Проверка, которая нужна только из-за ограничения одной платформы или одного редактора, живёт под директивой этой платформы (`#if UNITY_EDITOR_LINUX`), а причина пишется в тексте лога, а не комментарием. На остальных платформах такая ситуация остаётся ошибкой настройки и падает громко.

## Логирование и диагностика
- Для логирования инжектировать `ILogger`; предпочитать `_logger.Log(this, "...")` вместо прямого `Debug.Log`.
- Не дублировать источник лога в тексте сообщения (`[Notifications]`, `[Shop]`), если источник уже передаётся через `this`.
- Отладочные логи на каждое событие SDK (загрузилось, показалось, кликнули, развернулось) в коде не держать: для диагностики у SDK есть свой подробный режим логов. Лог остаётся только там, где без него ошибка потеряется, например в наблюдателе фоновой задачи.

## Редакторные скрипты
- Editor-классы делать `static`, если это только меню-команды или helper-функции.
- Menu-команды регистрировать через `[MenuItem("Rokot Games/...")]`.
- Editor-скрипты обычно работают с `PlayerPrefs`, файловой системой проекта или selection state; перед потенциально разрушительными действиями ставить проверки и логировать результат через общий logger.
- Внутренние scroll-области внутри editor tools (`EditorWindow`, custom tools) прятать под foldout/collapse, чтобы они не перехватывали основной scroll окна в обычном состоянии.
