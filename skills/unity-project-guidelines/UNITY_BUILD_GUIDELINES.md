# Unity Build Guidelines

Этот документ фиксирует практические правила по сборкам Unity-проекта.

- Именованные ссылки в `references` файла `.asmdef` брать из поля `name` фактического `.asmdef` пакета, а не из package ID: у `com.unity.ugui` сборка называется `UnityEngine.UI`. Проверять сами `.asmdef`: сборка через игнорируемые `.csproj` может скрыть неверную ссылку.

## Сборка принятой версии

- Для билда принятой работы и задач «В тесте» сверить актуальную вершину `origin/main` и взять её точную ревизию. Если текущий checkout содержит локальные правки или стоит на ветке открытого PR, использовать чистый checkout этой ревизии. Так артефакт соответствует уже влитым изменениям.
- На просьбу «подними версию и собери» один раз применить штатное повышение версии для целевой платформы в панели проекта. Сверить изменённые поля и зафиксировать только версию отдельным коммитом по [правилам коммитов](GIT_WORKFLOW.md#правила-коммитов). Прямой коммит и push в `main` допустимы по явному разрешению владельца на эту операцию и только для коммита версии. Повтор той же сборки использует уже зафиксированную версию.
- Для тестовых треков Google Play собирать AAB штатной кнопкой `Build AAB`. Для прямой установки на устройство собирать APK.
- Для проверки игровой логики на Android рядом с уже установленной версией собери QA APK с временным ID приложения в изолированной копии проекта. Перед установкой сверь ID, чтобы у QA и обычного приложения были разные данные. Обновление со старым сейвом проверяй на тестовом профиле через сборку с тем же ID и совместимой подписью.
- Запустить сборку из точной зафиксированной ревизии. Подтвердить успех по журналу сборки и сверить платформу, идентификатор приложения и версию по метаданным свежего артефакта. В ответе назвать ревизию и путь к файлу. Установка на устройство и публикация артефакта выполняются по отдельному запросу.
- Если в задачу входит синхронизация открытых PR, после сборки обновить их базы по [правилам цепочек PR](GIT_WORKFLOW.md#цепочки-pull-request) и сверить, что состав изменений каждого PR сохранился.
- Если команда называет тестовые билды номером из тулкита, короткую сводку для Telegram начинай с «Билдик N в сторе для тестеров!» после подтверждения доступности в сторе. Для готового артефакта до подтверждения пиши «Билдик N готов для тестеров!». N — пользовательский номер сборки из тулкита.
- После пустой строки оставь главное из подтверждённых изменений, по одной короткой строке в терминах игры. Связанные правки объединяй по игровому смыслу. Начинай строки с «Добавили», «Обновили» или «Исправили». Для билда с одной конкретной проверкой достаточно строки «Смотрим…» или «Тестим…». Пиши без маркеров, подзаголовков и точек в конце строк.
- Если условие установки или проверки важно для тестера, вынеси его в отдельный абзац. Например, предупреди о сбросе прогресса при обновлении. Перед отдачей перечитай сводку глазами тестера и оставь то, что помогает увидеть изменение или понять, что проверять. Номера PR, детали реализации, планы и полный список правок оставляй за пределами сводки.

## Чистая сборка

`Clean Build` использовать, когда player build не отражает последние изменения, особенно после правок в:

- Unity license, Unity Hub license state или версии Editor.
- `Player Settings`, splash screen, scripting backend, stripping, compression или build symbols.
- Android Gradle templates, SDK/NDK/JDK, plugins, Firebase, Ads, analytics SDK или generated local Maven repositories.
- Build size cleanup, asset stripping, `Resources`/Addressables-like content, render pipeline settings или shader settings.
- Unity version upgrades или package upgrades, которые затрагивают player/runtime code.

Обычная Unity-сборка может переиспользовать cached player data. Если в `Editor.log` есть:

```text
Information on used Assets is not available, since player data was not rebuilt.
Do a clean build to view the Asset build report information.
```

значит player data не был полностью пересобран, даже если UI-действие выглядело как clean/rebuild. Такой APK/AAB не считать доказательством, что настройки реально применились.

## Сброс кешей Android

Если `Clean Build` всё равно переиспользует старый Android player data, закрыть Unity и удалить generated cache folders:

```text
src/<проект>/Library/PlayerDataCache/Android
src/<проект>/Library/Bee/Android
src/<проект>/Library/Bee/artifacts/Android
src/<проект>/Library/BuildPlayerData
```

После этого открыть Unity заново и запустить `Build And Run` или собрать свежий APK/AAB.

## Чеклист симптомов

Сначала пробовать `Clean Build`, если:

- Watermark, splash screen, icon, version, signing, permission или manifest change на девайсе выглядят по-старому.
- APK/AAB size не меняется после удаления assets или SDK.
- Android install запускает билд, который ведёт себя как старая сборка.
- Build logs показывают, что player data was not rebuilt.

## Сборки через MCP

- Сервер Unity MCP повторяет команду до шести раз, если Unity не ответил за отведённое время, и Unity выполняет все копии по очереди. Долгая команда в `execute_code` (сборка, переключение платформы) поэтому запускается несколько раз подряд, а iOS-сборка панели перед экспортом удаляет папку прошлого экспорта.
- Любой такой вызов начинается с защиты от повтора: уникальный id запуска в `SessionState`, и если он уже стоит — немедленный выход. Без неё хук `mcp-long-command-guard.py` команду не пропустит.
- Ответ «Timeout receiving Unity response» не значит, что команда не выполнилась. Результат проверять маркером в `Editor.log` и считать маркеры `start`, а не вызывать команду ещё раз.
- Сборку запускать той же функцией, что и кнопка панели проекта. Свои шаги поверх неё не добавлять. Модальное окно в конце штатное: его закрывает владелец.
- Файлы на рабочем столе проверять из Unity (`System.IO` в `execute_code`) или точечным чтением конкретных путей. Список папки из песочницы ассистента бывает неполным.
