# Интеграционные рекомендации (Assets/Code)

Этот документ фиксирует правила и выводы по интеграции и отладке внешних SDK и плагинов.

## Установка SDK

- SDK ставится из официального дистрибутива по документации вендора: его способом установки (UPM или `.unitypackage`), со всеми модулями, которые документация требует для наших платформ, с зависимостями Android и iOS, разрешениями манифеста и файлами конфигурации. Документацию читают до установки и по ней же сверяют результат. Проект команды с тем же SDK подсказывает версию и вариант установки, но файлы SDK из него не копируют: копия переносит его пропуски, ручные правки и пути, которых нет в пакете, и сверить её не с чем. Пример: Firebase перенесли папками из соседней игры без нативных библиотек редактора (около 300 МБ через LFS). Пропуск всплыл только на живом запуске: Firebase упал при загрузке и оборвал запуск остальных SDK. Модуль Google для DevToDev при этом лёг не по пути своего пакета.
- Сразу после установки сверь файлы проекта со списком пакета: у пакетов Google это `<Продукт>_version-<версия>_manifest.txt`, у `.unitypackage` — его содержимое. У каждого отличия есть причина: файл исключён `.gitignore` (`*.pdb`), копия EDM в `Assets` не нужна, когда EDM стоит пакетом UPM, Unity пересохранил `.meta`, EDM переписал `.pom`, сменился перевод строк. Отсутствующий файл без такой причины — неполная установка. Большой бинарник идёт через LFS, а не выбрасывается. Механическую часть сверки со списком пакета Google выполняет `code-checks.py`.
- Значения по умолчанию в окне настроек SDK — не документация. Обязательные шаги платформ сверяй с документацией по тому, что реально попало в `mainTemplate.gradle` и `AndroidManifest.xml`. Пример: настройки Adjust по умолчанию не добавляют разрешение `ACCESS_NETWORK_STATE`, которое документация называет обязательным, и добавляют устаревшее `BIND_GET_INSTALL_REFERRER_SERVICE`.
- Сбой загрузки SDK чинится установкой, а не перехватом исключения в коде: перехват прячет неполную установку, и на другом компьютере она падает так же.

## Отладка сторонних SDK

- Если сторонний SDK или плагин работает некорректно, а в наших логах нет явной причины, сначала проверять, есть ли у вендора device/debug/verbose logs, и собирать именно их до любых изменений кода или настроек.
- На Android предпочитать `adb logcat`, а не только Lunar/Unity console, потому что ошибки native SDK могут появляться только в системных логах.
- Если у вендора есть инструкция уровня `Check your integration`, `Enable debug logs` или `Verbose logging`, проходить её в самом начале расследования.
- Тратить время на изменения кода, обновление SDK или гипотезы про backend/setup только после просмотра vendor-specific debug logs.
- Для JSON-диагностики в Editor не передавать универсальному сериализатору живые объекты FCU/Unity и их графы: свойства `UnityEngine.Object` и производные свойства векторов могут рекурсивно раскрывать новые объекты вплоть до падения Editor. Сохранять исходный JSON сетевого ответа либо явную проекцию нужных строк, чисел и массивов; у векторов выбирать только координаты `x/y/z/w`.

## Колбэки SDK и потоки

- Колбэки рекламных, платёжных и аналитических SDK могут приходить не с главного потока. Любые обращения к Unity API из таких колбэков переводить на Unity main thread через существующую инфраструктуру проекта.
- Не вызывать `FindAnyObjectByType`, `FindObjectOfType` и другие runtime-поиски из SDK-колбэков. Зависимости прокидывать заранее через DI, события или явные ссылки.

## Уроки DevToDev

- В кейсе с DevToDev Payments реальная причина проблемы не была видна, пока не включили `DTDLogLevel.Debug`.
- Без vendor debug logs ситуация выглядела как backend- или UI-проблема.
- После включения debug logs стало ясно, что `DTDPurchases.StartAutoTracking()` падал слишком рано с `null reference`.
