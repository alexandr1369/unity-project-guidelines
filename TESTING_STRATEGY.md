# Стратегия тестирования (Assets/Code)

Этот документ фиксирует правила и договорённости по тестам проекта.

## Зачем нужны тесты
- Тесты фиксируют ожидаемое поведение системы на момент, когда это поведение было признано правильным.
- Основная ценность теста — подсветить регрессию, когда поверх старой логики была добавлена новая и контракт незаметно изменился.
- Падение теста не означает автоматически баг в прод-коде: оно может означать и реальную поломку, и осознанное изменение поведения, при котором нужно обновить сам тест.
- Хороший тест проверяет один конкретный контракт и по возможности отсекает лишний flow соседних систем, чтобы падать только по своей причине.
- Тест — это не замена ручной проверки, а индикатор, который быстро показывает, что в конкретном сценарии поведение перестало совпадать с зафиксированным ожиданием.

## Интеграционные тесты в первую очередь
- Дефолт для новой фичи — интеграционный `PlayMode`-тест на сквозной сценарий плюс живой runtime-прогон. Юнит-тест заводить только если он попадает в разрешённую полосу ниже.
- Юнит-тесты (`EditMode`) допустимы для трёх случаев: save-format и сериализация persistent-состояния; чистые расчёты без движка (проценты, прогресс, математика, тайминги через подмену `ITimeProvider`); детерминированные инварианты сервисов, не трогающих Unity API.
- Gameplay-правила, которые живут в ECS-системах и зависят от состояния board/slot/chip, view, аниматоров или tween-ов, юнит-тестами не покрывать. Их приёмка — интеграционный `PlayMode`-тест или runtime-сценарий.
- Причина разделения: юнит-тест на gameplay-систему требует ручной сборки контекстов, view и аниматоров, ломается от любого рефакторинга и не доказывает поведение фичи. Интеграционный прогон проверяет ту же цепочку целиком и падает по делу.
- Признак, что юнит-тест писать не нужно: в `Arrange` появляется `GameObject`, `MonoBehaviour`, аниматор, tween-сервис или рефлексия.
- Признак, что юнит-тест нужен: поломка не видна ни глазами, ни интеграционным прогоном на свежих данных. Главный пример — переименование persistent-компонента, из-за которого у игроков молча слетает прогресс.
- Отсутствие юнит-теста не блокирует задачу. Не тормозить реализацию ради покрытия, которое не попадает в разрешённую полосу.

## Где лежат тесты
- Все тесты храним в кодовой зоне проекта: `Assets/Code/Tests`.
- `EditMode` тесты: `Assets/Code/Tests/EditMode`.
- `PlayMode` тесты: `Assets/Code/Tests/PlayMode`.

## Инструменты
- Базовый раннер: `Unity Test Framework`.
- Моки/стабы: `NSubstitute`.
- Читаемые проверки: `FluentAssertions`.
- Для проверок в тестах по умолчанию использовать `FluentAssertions` (`Should()`).
- `Assert.That` / `ClassicAssert` / `CollectionAssert` не использовать, если эквивалент можно выразить через `FluentAssertions`.
- Если для редкого кейса нужен `Assert`, это нужно явно прокомментировать в тесте, почему `FluentAssertions` недостаточно.

## Базовый стиль тестов
- Писать тесты в формате `When...Then...` и по схеме `Arrange / Act / Assert`.
- Это правило едино для всех тестов: и `EditMode`, и `PlayMode`; для интеграционных (`PlayMode`) тестов его соблюдение особенно обязательно.
- В каждом тесте обязательно использовать структуру `Arrange / Act / Assert` и комментарии секций с заглавной буквы: `// Arrange`, `// Act`, `// Assert`.
- `// Act` обязателен, когда в тесте есть отдельный явный шаг действия над SUT; если отдельного шага нет и действие слито с подготовкой, допустимо оставить только `// Arrange` и `// Assert`.
- Наличие `_And` в имени теста не связано с `// Act`: `_And` описывает условие в названии, `// Act` описывает шаг действия в теле теста.
- Именовать тесты как `When<Condition>_Then<Expectation>`; `_And<ExtraCondition>` использовать точечно, только когда это реально повышает читаемость и влияет на ожидание.
- Не добавлять `EditMode`/`PlayMode` в имя тест-класса: режим уже отражён папкой и namespace.
- Для `EditMode` классов использовать имя SUT (`<SutName>Tests`), для `PlayMode` — имя фичи/сценария (`<FeatureName>Tests`).
- Не добавлять суффиксы `Unit`/`Integration` в имя тест-класса, если режим уже однозначно определяется папкой/asmdef.
- В `PlayMode` держать `Arrange` максимально в теле теста, чтобы сценарий читался сверху вниз без переходов по helper-методам.
- В `PlayMode` делить `Arrange` на 3 смысловых блока: `Resolve dependencies` -> `Domain setup` -> `Entry setup`.
- Между смысловыми блоками ставить ровно один пустой ряд; внутри блока пустые строки не ставить.
- В блок `Resolve dependencies` входят все исходные данные, получаемые в начале `Arrange`: как прямые `Container.Resolve(...)`, так и значения, извлечённые из уже resolved-зависимостей (например, `staticDataService.Get...Config()`).
- Внутри `Resolve dependencies` не делать дополнительного разделения пустыми строками между `Resolve` и извлечёнными из них данными.
- В `Act` и `Assert` не добавлять лишние пустые строки.
- Выносить в helper-методы только общий инфраструктурный setup/teardown, который реально переиспользуется между тестами.
- В `SetUp`/`TearDown` допускается выносить инфраструктурные helper-методы даже при одном вызове, если это убирает шум и не прячет доменный сценарий теста.
- В `SetUp` использовать 2 смысловых блока: инфраструктурный reset (`snapshot/clear`) -> тестовые preconditions (конфиги/входные значения перед загрузкой сцены).
- Не выносить доменную подготовку конкретного теста в отдельные `Prepare...` методы, если это ухудшает навигацию по сценарию.
- Общие/reused константы хранить в профильных файлах (`PlayModeConstants`, `EditModeConstants` и т.д.); константы уровня конкретного сценария хранить в самом тест-классе.
- Не объявлять `const` внутри тест-методов. Если значение нужно переиспользовать или назвать, поднимать его на уровень тест-класса; если значение одноразовое, использовать обычную локальную переменную.
- Избегать магических значений; именованные переменные вводить только для ключевых значений сценария.
- Проверять наблюдаемое поведение/состояние, а не внутренние вызовы реализации.
- Не добавлять защитные проверки, которые не влияют на критерий готовности/результат теста.
- Внутри тест-класса порядок публичных методов: `SetUp`/`UnitySetUp` -> тесты -> `TearDown`/`UnityTearDown`.

## PlayMode (интеграционные) тесты
- Каноничный запуск PlayMode suite: `scripts/run_playmode_isolated.sh` (по одному тесту в отдельном Unity-процессе).
- Массовый запуск PlayMode внутри открытого Editor не считать источником истины из-за межтестового state pollution.
- В Editor запускать PlayMode тесты точечно для локальной отладки сценария.
- Все batch-запуски Unity тестов (`EditMode` и `PlayMode`) выполнять только при закрытом Editor на этом `projectPath`; второй Unity-инстанс на том же проекте упирается в `project lock`.
- Все batch-запуски Unity тестов из Codex выполнять вне sandbox (`require_escalated`), потому что sandbox может ломать `Unity LicensingClient IPC` и давать ложные падения раннера.
- `run_editmode.sh` запускает весь `EditMode` набор одним Unity batch-процессом.
- `run_playmode_isolated.sh` даже при `--jobs=1` запускает один Unity batch-процесс на один `PlayMode` тест; отдельные project clones используются только при `--jobs>1`.
- Для full-flow сценариев использовать реальные сервисы из `ProjectContext` и реальный state flow.
- `NSubstitute` применять точечно для внешних границ (SDK/сеть/реклама), но не для ядра доменной логики, которую проверяет тест.
- Ожидания делать через цикл по условию (`while` + условие), а не через фиксированные `WaitForSeconds`.
- Работа с stateful хранилищами (например, `PlayerPrefs`) должна идти через тестовые helper-сервисы со snapshot/restore, чтобы не дублировать cleanup в каждом тесте.
- Проверки делать через публичный API сервиса/фичи; прямую правку `ProgressData` использовать только как технический setup, когда это неизбежно.
- Базовые значения для `Assert` фиксировать после полного `Arrange` и до `Act`, чтобы не получить ложноположительный результат.
- Для активации/инициализации фичи использовать осмысленные значения из конфигов, а не магические константы.
- Entitas feature-тесты писать через `DiContainer` + тестовый `Installer` + `ISystemFactory.Create<Feature>()`, а не прямой `new System(...)`, если проверяется порядок систем, очередь action-ов или взаимодействие нескольких ECS-шагов.
- В Entitas PlayMode-тестах binder contexts должен использовать текущий `Contexts.sharedInstance`; тест в `SetUp` создаёт свежий `Contexts`, installer биндинит `Contexts`, `GameContext`, `InputContext`, `MetaContext`, а `TearDown` завершает lifecycle фичи (`DeactivateReactiveSystems`, `ClearReactiveSystems`, `Cleanup`, `TearDown`) и сбрасывает `Contexts.sharedInstance`.
- В Entitas PlayMode-тестах конкретный доменный сценарий держать в теле теста: создание slot/chip/action entities, входной input и ожидания должны читаться в `Arrange / Act / Assert`, а в installer выносится только инфраструктура и подмены внешних границ.

## Как выбирать режим теста
- `PlayMode` использовать для проверки сквозного пользовательского сценария (сцены, state machine, DI, переходы между состояниями).
- `EditMode` использовать для детерминированной проверки расчётов и ветвлений внутри разрешённой полосы из `Integration First` (пороги, даты, edge-cases, математические расчеты, сериализация).
- Временные сценарии (`NowUtc`, переход на следующую дату, истечение таймера) по умолчанию проверять в `EditMode` через подмену `ITimeProvider`.
- В `PlayMode` не мокать ядро проверяемой фичи; моки допустимы для внешних границ и недетерминированных источников (время, сеть, SDK, реклама).
- Выбирать режим не по признаку `meta/gameplay`, а по цели проверки: нужна ли реальная интеграция Unity-цикла (`PlayMode`) или проверка правил/ветвлений (`EditMode`).
- Если сценарий требует "прокрутки" большого времени (минуты/часы/дни), это `EditMode`; если сценарий укладывается в короткий реальный прогон в рантайме, это `PlayMode`.
- Для time-based фич держать баланс: один `PlayMode` smoke-тест на сквозной флоу + детальные edge-case проверки времени в `EditMode`.
- Если нужно проверить, что runtime-UI корректно реагирует на событие/тик сервиса (показ/скрытие блока, перестройка layout), это `PlayMode`.

## Ментальная модель (как быстро выбрать тип теста)
- Думать в терминах "события vs воронка":
- `EditMode` = проверка отдельного события/правила (локальная логика одного шага).
- `PlayMode` = проверка воронки (сквозной runtime путь из нескольких шагов и их стыков).
- Для каждой фичи по умолчанию: 1-2 `PlayMode` smoke на ключевые сквозные ветки; `EditMode` добавлять только на расчёты и сериализацию.
- Вопрос для выбора: "я проверяю правило внутри шага или прохождение всей цепочки между шагами?".
- Если проверяется правило внутри шага — это `EditMode`; если проверяется прохождение цепочки между шагами — это `PlayMode`.

## Моки и границы
- В `PlayMode` не мокать ядро проверяемой фичи; иначе теряется смысл интеграционного прогона.
- В `PlayMode` моки допустимы только на внешних границах (SDK/сеть/реклама/недетерминированные источники).
- В `EditMode` моки использовать свободно для локализации проверки правила и упрощения setup.

## Антипримеры
- Не использовать рефлексию в тестах для доступа к private-полям UI (например, к private `Button` в диалоге).
- Не менять прод-код только ради обхода UI в тесте, если можно воспроизвести корректное состояние через `ProgressData` и закрыть диалог публичным API (`Close()`).

## Пример структуры Arrange
```csharp
// Arrange
IServiceA serviceA = Container.Resolve<IServiceA>();
IServiceB serviceB = Container.Resolve<IServiceB>();

serviceA.Enable();
serviceB.Seed(10);

stateMachine.Enter<SomeState>();
yield return new WaitUntil(IsReady);
```

## Правило для сложных выборок
- Для многошаговых выборок разрешено использовать `LINQ` (в том числе query syntax: `from`, `where`, `select`, `group by`), если это делает тест короче и понятнее.
- Если `LINQ`-цепочка становится плохо читаемой, разбивать её на 2-3 именованных шага.

## Пример подхода (не обязательное правило)
- Пример: проверка `Missing Scripts` по нашим сценам (`Assets/_Scenes`) в `EditMode`.
- В сложных проходах выносить основную логику в helper-методы (`OpenProjectScenes`, `GetAllGameObjects`, `HasMissingScripts` и т.д.), а в тесте оставлять короткий читаемый pipeline.
- Если уместно, использовать `LINQ` и `group by` для компактного отчёта (например, группировка по сцене и имени объекта).
- Финальная проверка должна оставаться простой и читаемой (`Should().BeEmpty(...)` или аналогичное целевое условие).
