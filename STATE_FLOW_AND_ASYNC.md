# Потоки состояний и асинхронность

Этот документ фиксирует обязательные архитектурные правила для state flow, длительных операций, прогресса загрузки и границы между инфраструктурой и Unity presentation layer.

## Владение потоком
- Все машины состояний наследуют общую базу и не изобретают собственный набор методов. Контракт задаёт сама база, отдельный интерфейс поверх неё не заводится. Публичный набор закрытый: `Tick()` — тик активного состояния, `Enter<TState>()` — переход, `Enter<TState, TPayload>()` — переход с данными, `CleanUpAsync()` — гашение машины со штатным выходом активного состояния.
- Наследник добавляет только то, что действительно его: например, прогон собственной feature внутри `Tick()`. Переименовывать методы контракта под себя (`Handle` вместо `Tick`, `CleanUp` вместо `CleanUpAsync`) запрещено — от этого три машины перестают читаться как одна.
- Второго способа гашения быть не должно. Бросать активное состояние, не вызвав его выход, нельзя: его `Exit` не отработает, а это не оптимизация, а пропущенная очистка.
- Логирование входа в состояние принадлежит базе, а не наследнику: формат один на все машины.

- State владеет порядком действий, ветвлением, переходом в следующий state и моментом публикации прогресса своего сценария.
- Последовательность state должна читаться сверху вниз непосредственно в `Enter`. Вынесенные методы допустимы только для именования самостоятельных частей сценария; они не должны скрывать порядок вызовов.
- State machine владеет минимальным жизненным циклом: штатно выходит из текущего state, назначает ровно один новый активный state, синхронно вызывает его `Enter` и логирует переход. Машина не ждёт завершения `Enter`, не отменяет его продолжение и не сериализует запросы поверх предметного flow.
- Service предоставляет законченную capability своего домена. Service может координировать собственные внутренние детали, но не исполняет сценарий вызывающего state и не выбирает следующий state.
- Presentation service владеет только визуальным состоянием и визуальными переходами. Он не выполняет gameplay/domain actions и не определяет порядок загрузки.
- View и animator не входят в state machine и не принимают решения о следующей фазе предметного flow. Чистую UI-навигацию view может вызвать напрямую; перед вызовом она сразу блокирует одноразовый control, чтобы повторный UI event не превратился в повторный запрос перехода.

## Линейный поток состояний
- Каждое действие размещать ровно в той точке `Enter`, где оно должно произойти.
- Переход в следующий state размещать последним видимым действием успешного сценария.
- Не передавать из state в service массивы или коллекции `Action`, `Func<Task>`, `IEnumerator` и других исполняемых шагов.
- Не передавать в service callback, который продолжает state flow или выполняет переход. Ожидаемая операция возвращает `Task`; синхронная операция завершается возвратом из метода.
- Callback допускается только на локальной границе API, которое иначе завершение не предоставляет: SDK event, Unity callback или адаптер coroutine. Такой callback преобразуется в ожидаемую операцию внутри адаптера и не выходит в контракт state.
- Не прятать важный порядок в generic-методах вида `Process`, `Handle`, `CompleteStage` или `ExecuteSteps`. Название вынесенного метода должно описывать конкретное действие.
- Не хранить продолжение flow во флагах «уже выполнено», отложенных callback или повторных проверках. Если порядок известен, он выражается порядком строк.
- Не добавлять delay, ожидание кадра или polling для исправления неверного порядка. Сначала перенести действие в правильную точку flow.

## Модель асинхронности
- Синхронный код оставлять синхронным. `async` не является обязательным признаком state или service.
- Для асинхронных контрактов infrastructure service, domain service, SDK, I/O и сохранений использовать `Task`/`Task<T>` и `CancellationToken`. Контракт входа state остаётся синхронным `void Enter()` и не превращает сам переход в ожидаемую операцию.
- Конкретный state, чей линейный сценарий содержит реальные ожидания, реализует `async void Enter()`: это осознанная lifecycle-граница, потому что машина активирует state, но не владеет завершением его сценария. Другие `async void` в state и service запрещены.
- После `await` state продолжает только собственный линейный сценарий и последним действием запрашивает следующий state. Исключения из `async void Enter()` не перехватывать пустым observer-ом: необработанная ошибка обязана попасть в Unity console; ожидаемые предметные ошибки обрабатывать и логировать внутри самого state.
- Любая другая fire-and-forget операция без владельца и обработки исключения запрещена. Если вызывающая сторона не ждёт `Task`, отдельный observer обязан дождаться его, обработать отмену и залогировать ошибку.
- Не оборачивать синхронную работу в `Task.Run`, если она обращается к Unity API, `UnityEngine.Object`, scene objects, DI context или view.
- Не опрашивать `Task.IsCompleted` из coroutine. Если операция возвращает `Task`, ожидать её через `await`.
- Не использовать `Task.Yield`, `Awaitable.NextFrameAsync` или нулевой delay как универсальный способ «дать Unity отрисоваться».
- `Awaitable` использовать точечно только для настоящей Unity-границы: `AsyncOperation`, ожидания конкретной фазы Player Loop или Unity API, которое уже возвращает `Awaitable`.
- Если требуется именно конец кадра, это требование должно быть предметным и явным. Во view использовать `WaitForEndOfFrame`; в асинхронной инфраструктуре допустим `Awaitable.EndOfFrameAsync`. `Task.Yield` не считать эквивалентом конца кадра.
- Если точная фаза Player Loop не важна, не добавлять ожидание кадра вообще.
- Ожидание кадра после тяжёлого синхронного метода не разгружает этот метод. Сначала профилировать и делить саму операцию на самостоятельные части.

## Граница корутин
Этот блок перечитывать перед любым изменением, которое добавляет `IEnumerator`, `StartCoroutine` или `ICoroutineRunner`.

- Граница ровно одна: coroutine живёт **только** в `MonoBehaviour` (view, animator, screen, effect), который сам ею владеет. Всё остальное — state, state machine, infrastructure service, domain service, provider, factory, adapter — использует `async`/`await` и `Task`.
- Coroutine запускается через `StartCoroutine` того же `MonoBehaviour` и останавливается в его lifecycle cleanup. Это единственный допустимый владелец coroutine.
- Метод, возвращающий `IEnumerator`, именовать с суффиксом `Coroutine`.
- Не оборачивать coroutine в `Task` через `TaskCompletionSource`, callback или любой другой adapter. Такая обёртка запрещена: если операция нужна вызывающей стороне как ожидаемая, она пишется на `async`/`await` целиком, а не заворачивается.
- Не оборачивать `Task` в coroutine: `yield return new WaitUntil(() => task.IsCompleted)` и любой polling `Task` из coroutine запрещены.
- `ICoroutineRunner` остаётся в инфраструктуре как часть базы проекта: контракт объявлен в `Code.Infrastructure`, реализует его `BootstrapInstaller`. Он не удаляется из-за отсутствия потребителей — это единая точка запуска корутины для тех редких случаев, когда она понадобится вне `MonoBehaviour`-view. Это осознанное исключение из общего запрета держать код без вызывающих.
- Наличие контракта не разрешает им пользоваться по умолчанию: новый код по-прежнему пишется на `async`/`await` и `Awaitable`, а загрузка сцен и ожидания через корутины не возвращаются.
- `ICoroutineRunner` не инжектировать в state и service. Persistent runner остаётся только у тех редких `MonoBehaviour`, которым нужен coroutine, переживающий собственный объект; новые зависимости от него не добавлять.
- Ожидание внутри async-кода писать на Unity-примитивах, а не на coroutine: `await Awaitable.NextFrameAsync(token)` для покадрового опроса состояния, `await Awaitable.EndOfFrameAsync(token)` для конца кадра, `await Awaitable.WaitForSecondsAsync(seconds, token)` для паузы, `await operation` для `AsyncOperation`/`ResourceRequest`.
- Покадровый `await Awaitable.NextFrameAsync(token)` допустим только как явный опрос внешнего состояния, которое не даёт события (флаг animation event, native SDK, `AsyncOperation.progress`). Как способ «дать Unity отрисоваться» он по-прежнему запрещён.
- Если `MonoBehaviour`-view должен быть ожидаемым для state, view сам объявляет `async Task`-метод или событие завершения. Появление `TaskCompletionSource` в state или service — сигнал, что граница нарушена.
- `async` во view разрешён, но с жёстким ограничением: **ожидание внутри `MonoBehaviour` строится только на `Awaitable` или корутине**. И то и другое привязано к player loop и умирает вместе с ним, поэтому форма записи (`await` или `yield return`) роли не играет — играет привязка к кадру Unity.
- Во view запрещены `Task.Delay`, `Task.Run`, `ContinueWith`, работа в потоках и любое другое ожидание вне player loop. Такое ожидание переживает выход из Play Mode и уничтожение объекта, и именно оно, а не ключевое слово `async`, является нарушением границы.
- Причина, по которой ожидаемый метод view пишется на `Awaitable`, а не на корутине: `await` на корутину в C# невозможен. Обратное направление работает — `Awaitable` можно `yield return`-ить внутри корутины. Поэтому view, которое должно быть ожидаемым для state, пишется на `Awaitable` целиком, а не заворачивается в мост.

## Инструменты асинхронности
- Для ожидания Unity использовать `Awaitable`: `NextFrameAsync` для покадрового опроса, `EndOfFrameAsync` для конца кадра, `WaitForSecondsAsync` для паузы, прямой `await` для `AsyncOperation`. Для ожидания работы (I/O, фоновый поток, SDK) использовать `Task`. Смешивать их в одном методе допустимо.
- Сторонние async-библиотеки (UniTask и аналоги) не добавлять. `Awaitable` покрывает нужные фазы Player Loop, приходит вместе с движком и не отстаёт при апгрейде Unity, а переход на сторонний тип задачи меняет сигнатуры во всех контрактах проекта ради выигрыша, которого у нас нет.
- Помнить ограничения `Awaitable`: `WaitForSecondsAsync` считает по `timeScale` (для realtime-таймаутов ожидание строить на `ITimeProvider`), в Edit Mode `Awaitable` не резолвится (состояния с ним не покрываются EditMode-тестами), один экземпляр ожидается один раз.

## Время жизни состояний
- Штатный flow не запрашивает новый переход, пока текущий `Enter` не дошёл до своего последнего действия. Если нужны параллельные локальные режимы, это отдельные state machine, а не несколько одновременно активных state одной машины.
- Общая машина не хранит очередь, async-затвор, transition request, generation/token текущего входа и не вводит `TryEnter`: эти конструкции решают запрещённый для текущего проекта конкурентный flow и усложняют обычный последовательный путь.
- Дребезг пользовательского ввода гасится в source-view: одноразовая кнопка блокируется до публикации request или прямого перехода, а curtain блокирует ввод на визуальном переходе. Машина не должна угадывать, какой из двух переходов считать правильным.
- Если переход могут независимо запросить несколько не-UI источников, их владелец обязан сначала свести событие к одному решению. Добавлять глобальную защиту в машину вместо явного владельца конфликта нельзя.
- Выход текущего state всегда ожидается до назначения следующего. Асинхронный выход допустим только при реальной причине — например, чтобы длительно живущий loop-state завершил текущий кадр; на это время сам такой базовый state не пропускает свой `Update`.
- Машина не прячет исключения выхода в observer-обёртке. `CleanUpAsync` возвращает ожидаемый `Task` вызывающему коду, а ошибка перехода из `async void Enter` остаётся видимой в Unity console.
- Состояние, чей `Enter` ждёт операцию, способную пережить его выход, само создаёт `CancellationTokenSource`, передаёт токен по своей цепочке ожиданий и отменяет его в `Exit`; машина токенов не раздаёт.
- Собственный `CancellationToken` объекта (`MonoBehaviour.destroyCancellationToken`) — не исключение из правила, а его частный случай: это время жизни самого объекта, а не токен, протянутый через контракты. Использовать там, где ожидание переживёт уничтожение объекта.
- View coroutine, tween, event subscription и SDK request должны иметь симметричный cleanup, если способны пережить активный state.

## Прогресс загрузки
- State владеет реальными шагами загрузки и явно вызывает каждый из них.
- Прогресс шага публиковать только после успешного завершения соответствующего действия.
- Диапазоны этапов и перевод локального прогресса этапа в общий процент хранить в loading progress config/calculator, а не хардкодить в state.
- Компонент расчёта прогресса не исполняет шаги, не меняет state и не решает, когда скрывать curtain.
- Curtain service принимает готовое визуальное значение прогресса и управляет только отображением, визуальной анимацией заполнения и видимостью curtain.
- Визуальные методы называть по видимому эффекту: `ShowProgress`, `SetProgress`, `ShowCompletedProgressAsync`, `Hide`. Имя обязано пережить смену реализации: если метод перестал анимировать заполнение и стал доводить полосу до ста процентов, он переименовывается вместе с поведением.
- Не выдерживать искусственных пауз ради «красоты». Если работа закончена, curtain скрывается сразу; единственное допустимое ожидание на этой границе — дать отрисовщику показать финальное значение прогресса.
- Скорость движения полосы задаётся одним параметром. Отдельной длительности «дозаполнения» быть не должно: финиш идёт той же скоростью и занимает ровно столько, сколько осталось пройти. Длительность вычисляет сама curtain по своему фактическому положению, а не подбирается в конфиге.
- Полоса загрузки обязана видимо доходить до ста процентов до того, как curtain скрыта. Доведение и скрытие — разные шаги state, потому что между ними находится запуск раскрытия: музыка, появление контента и звук должны начинаться после сотни и совпадать со снятием curtain, а не звучать под ней.
- Установка финального значения прогресса без отрисовки кадра не считается показом. Если значение выставлено и curtain скрыта в том же кадре, игрок увидит последний отрисованный процент, а не сто.
- Обновление progress bar само по себе не требует ожидания следующего кадра. Frame boundary добавлять только при осознанном разбиении реальной работы между кадрами.
- Если curtain не показан, шаги state всё равно исполняются в том же порядке. Видимость curtain не должна выбирать функциональный сценарий.
- Окончание загрузки и визуальное окончание curtain — разные события. State заканчивает загрузку; curtain service проигрывает конкретно запрошенный визуальный эффект.

## Ревью контрактов сервисов
Новый или изменённый service contract нельзя принимать, пока на каждый вопрос нет однозначного ответа:

1. Какая одна capability принадлежит service?
2. Не передал ли caller внутрь service собственный порядок действий?
3. Не выбирает ли service следующий state или продолжение чужого flow?
4. Может ли caller прочитать свой сценарий сверху вниз без перехода в implementation service?
5. Возвращает ли длительная операция ожидаемый результат вместо callback?
6. Кто отменяет операцию при выходе из state, смене сцены и выходе из приложения?
7. Кто наблюдает исключение?
8. Требуется ли реальная Unity frame boundary или ожидание добавлено для маскировки порядка/нагрузки?
9. Описывает ли имя метода фактический эффект, а не абстрактное «завершение процесса»?

## Поводы для рефакторинга
Следующие конструкции требуют остановить текущую реализацию и сначала пересмотреть границы ответственности:

- `Action[]`, `Func<Task>[]` или список coroutine передаётся из state в service;
- service принимает callback перехода в следующий state;
- state ждёт `Task` через polling в coroutine;
- `IEnumerator`, `StartCoroutine` или `ICoroutineRunner` появляются в файле, который не является `MonoBehaviour`;
- `TaskCompletionSource` используется, чтобы превратить coroutine в `Task`;
- infrastructure flow зависит от coroutine на persistent runner без явной отмены;
- `async void` находится в service или в state вне единственного lifecycle-метода `Enter`;
- контракт state возвращает `Task`, а машина ждёт вход, хранит очередь переходов, async-затвор, transition token или `TryEnter`;
- после каждого действия без предметной причины стоит `yield return null`, `Task.Yield` или `Awaitable.NextFrameAsync`;
- один метод одновременно выполняет domain actions, считает progress и управляет curtain;
- тяжёлая синхронная операция объявляется исправленной только потому, что до или после неё добавлен `await`;
- название `Complete` скрывает несколько разных эффектов или продолжение чужого flow.

## Чек-лист изменений
Перед завершением изменения state flow обязательно проверить:

1. Сценарий виден в state одной последовательностью.
2. Переход в следующий state — последнее действие его текущего последовательного сценария.
3. UI-control блокирует повторный одноразовый запрос до передачи управления curtain/state flow.
4. Длительные операции внутри state ожидаются, а ожидаемые ошибки обрабатываются; неожиданные ошибки видны в Unity console.
5. View содержит только presentation behavior.
6. Services не получили управление caller flow.
7. Progress соответствует реально завершённой работе.
8. Frame waits имеют конкретную Unity-причину.
9. Скрытая и показанная curtain не меняют функциональный порядок.
10. Тесты проверяют синхронную активацию, порядок exit -> next enter, payload и штатный cleanup.
